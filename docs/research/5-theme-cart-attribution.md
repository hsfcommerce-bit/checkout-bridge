# Online Store theme side: Ajax Cart API, checkout triggers (cart form, accelerated checkout buttons), cart permalinks, cross-domain attribution and cookies (researched 2026-10-05 against shopify.dev, help.shopify.com, shopify.com/legal, Shopify changelog; Shopify-authored Dawn/Horizon theme source and Meta/Google/TikTok vendor docs used where Shopify docs are silent, and labelled as such)

Researched on 2026-10-05 from Shopify primary documentation. Each claim was re-checked by an independent verifier;
the verdict is shown in brackets. "CORRECTION" lines override the claim they follow. Items marked community/RISK are not official.

## Claims

- **V-01** [confirmed, confidence high] 2026-10 is the latest stable Shopify API version (released October 1, 2026, accessible until October 16, 2027 15:00 UTC). 2027-01 is the release candidate. 2026-01, 2026-04 and 2026-07 are still stable; 2025-10 is listed as unsupported.
  Source: https://shopify.dev/docs/api/usage/versioning
- **V-02** [confirmed, design-critical, confidence high] The Ajax API (used by the theme script) is unauthenticated: no access token or client ID. It has no hard rate limit but is subject to abuse-prevention. It is not presented with an API version on the reference pages (versioning of the Ajax API: not documented).
  Source: https://shopify.dev/docs/api/ajax
- **AJ-01** [confirmed, confidence high] GET /{locale}/cart.js returns the cart as JSON. Top-level keys in the documented example, in order: token, note, attributes, original_total_price, total_price, total_discount, total_weight, item_count, items, requires_shipping, currency, items_subtotal_price, cart_level_discount_applications.
  Source: https://shopify.dev/docs/api/ajax/reference/cart
- **AJ-02** [partially_correct, confidence medium] Each items[] entry in the documented /cart.js example has these keys: id, properties, quantity, variant_id, key, title, price, original_price, discounted_price, line_price, original_line_price, total_discount, discounts, sku, grams, vendor, taxable, product_id, product_has_only_default_variant, gift_card, final_price, final_line_price, url, featured_image, image, handle, requires_shipping, product_type, product_title, product_description, variant_title, variant_options, options_with_values, line_level_discount_allocations, line_level_total_discount, quantity_rule {min,max,increment}, has_components, and selling_plan_allocation {price_adjustments, price, compare_at_price, per_delivery_price, selling_plan} when the line has a selling plan. (Key list extracted from the example JSON, not from a field table.)
  Source: https://shopify.dev/docs/api/ajax/reference/cart
  **CORRECTION:** Key list matches the example JSON, but it is not complete: the second example item also carries `unit_price` and `unit_price_measurement` {measured_type, quantity_value, quantity_unit, reference_value, reference_unit} (unit-priced products), and `selling_plan_allocation` is absent (not null) on the line without a selling plan. There is still no field table, so the list is example-derived only. (https://shopify.dev/docs/api/ajax/reference/cart)
- **AJ-03** [confirmed, design-critical, confidence high] In the cart context a line item's `id` equals the variant ID and is not unique per line (the example shows id == variant_id == 39897499729985). The unique line identifier is `key` ("<variant id>:<hash>"), and keys are not stable: they change when line characteristics change. The middleware should read `variant_id` + `quantity` and must not treat `id` as a line identifier.
  Source: https://shopify.dev/docs/api/liquid/objects/line_item
- **AJ-04** [confirmed, design-critical, confidence high] All money fields in /cart.js (price, line_price, total_price, etc.) are in the buyer's presentment currency of the vitrine store, identified by the top-level `currency` field (example "CAD"). They are therefore market/currency dependent and unsuitable as a price source for the checkout store.
  Source: https://shopify.dev/docs/api/ajax/reference/cart
- **AJ-05** [confirmed, design-critical, confidence medium] Price units: the Ajax Cart reference page does not state the unit in prose; its example uses integers ("price": 900, "total_price": 2925). The Liquid cart/line_item reference, which describes the same objects, states the values are in the currency's subunit, and for zero-decimal currencies (JPY, KRW) tenths and hundredths are appended.
  Source: https://shopify.dev/docs/api/liquid/objects/cart
- **AJ-06** [confirmed, confidence medium] The `token` field appears only in the example response, with a value shaped like "<token>?key=<secret>". The Ajax reference gives no description of its semantics, lifetime or stability; do not build identity or idempotency on it without testing.
  Source: https://shopify.dev/docs/api/ajax/reference/cart
- **AJ-07** [confirmed, confidence high] `note` is a string and `attributes` is an object of key/value pairs in /cart.js (example: "note": "Hello!", "attributes": {"Gift wrap": "Yes"}). Private cart attributes (name prefixed with double underscore `__`) are NOT returned by the Ajax API or Liquid, so a theme script reading /cart.js cannot see or forward them.
  Source: https://shopify.dev/docs/api/ajax/reference/cart
- **AJ-08** [confirmed, confidence high] Line item `properties` is an object of name/value pairs. Properties whose key starts with a single underscore `_` are private: they ARE returned by the Ajax API and Liquid, are hidden at checkout, and are visible on the Order details page in admin.
  Source: https://shopify.dev/docs/api/ajax/reference/cart
- **AJ-09** [confirmed, design-critical, confidence high] A line carries `selling_plan_allocation` only when it was added with a selling plan (POST /cart/add.js `selling_plan` = selling plan ID). In Liquid the property is nil when there is no selling plan. The middleware must detect this field because subscriptions cannot be carried by the cart-permalink fallback (see PL-11).
  Source: https://shopify.dev/docs/api/ajax/reference/cart
- **AJ-10** [confirmed, confidence high] Ajax requests must be built from the locale-aware root `window.Shopify.routes.root`, which always ends with `/` (documented example: fetch(window.Shopify.routes.root + 'cart.js')). In Liquid the equivalent is the `routes` object (routes.root_url, routes.cart_url, routes.cart_add_url, routes.cart_change_url, routes.cart_clear_url, routes.cart_update_url).
  Source: https://shopify.dev/docs/api/ajax
- **AJ-11** [confirmed, confidence high] Hard-coding `/cart` or `/cart.js` drops the buyer's language/market context. Locale/market URL prefixes are subfolders such as shop.com/fr (language) and shop.com/en-ca (market).
  Source: https://shopify.dev/docs/storefronts/themes/markets/multiple-currencies-languages
- **AJ-12** [confirmed, confidence high] POST /{locale}/cart/update.js updates line quantities (`updates`), the note (`note` string), attributes (`attributes` object, or form field `attributes[Gift wrap]`), and discount codes (`discount`). The response is the cart JSON. An invalid variant ID returns {"status":404,"message":"Cart Error","description":"Cannot find variant"}.
  Source: https://shopify.dev/docs/api/ajax/reference/cart
- **AJ-13** [confirmed, design-critical, confidence high] Documented Ajax cart error shapes: 422 {"status":422,"message":"Cart Error","description":...} when quantity exceeds stock or the product is sold out; 404 "Cart Error" on add.js when the variant does not exist or is not available in the Online Store channel; change.js returns 400 for an item not in the cart.
  Source: https://shopify.dev/docs/api/ajax/reference/cart
- **AJ-14** [confirmed, design-critical, confidence high] Ajax API hard limits: it cannot read customer or order data nor update store data; product JSON responses are capped at 250 variants; bundled section rendering returns at most five sections.
  Source: https://shopify.dev/docs/api/ajax
- **AJ-15** [confirmed, confidence medium] POST /{locale}/cart/clear.js zeroes all line quantities but keeps cart attributes and the note. If the theme script clears the vitrine cart after handing off, attributes/note stay behind unless explicitly reset through update.js.
  Source: https://shopify.dev/docs/api/ajax/reference/cart
- **CK-01** [confirmed, design-critical, confidence high] The documented cart-to-checkout mechanism is a POST form: <form action="{{ routes.cart_url }}" method="post"> containing a submit control with name="checkout" (documented example: <input type="submit" name="checkout" value="Checkout" />). Cart note and attribute inputs outside the form attach with form="cart" (name="note", name="attributes[attribute-name]"). This is the control the theme script must intercept.
  Source: https://shopify.dev/docs/storefronts/themes/architecture/templates/cart
- **CK-02** [confirmed, design-critical, confidence high] The Liquid tag {% form 'cart', cart %} renders <form method="post" action="/cart" id="cart_form" accept-charset="UTF-8" class="shopify-cart-form" enctype="multipart/form-data"> with hidden inputs form_type=cart and utf8. Themes may use this instead of a hand-written form, so the script should match on form action (cart URL) plus submitter name `checkout`, not on a fixed form id.
  Source: https://shopify.dev/docs/api/liquid/tags/form
- **CK-03** [confirmed, design-critical, confidence high] Theme Store requirements make the checkout button a cart-form submit, and require accelerated checkout buttons on both product and cart pages, enabled by default. A freshly installed Theme Store theme therefore exposes checkout paths that bypass any custom script until they are turned off.
  Source: https://shopify.dev/docs/storefronts/themes/store/requirements
- **CK-04** [confirmed, confidence medium] The Liquid `routes` object exposes cart_url, cart_add_url, cart_change_url, cart_clear_url, cart_update_url, root_url and others, but no checkout URL property. A plain link to /checkout is not described in the theme documentation that was read.
  Source: https://shopify.dev/docs/api/liquid/objects/routes
- **CK-05** [confirmed, design-critical, confidence high] Dawn cart page (Shopify-authored theme source on GitHub, not a doc page): the form is in sections/main-cart-items.liquid with id="cart"; the checkout control is in sections/main-cart-footer.liquid: <button type="submit" id="checkout" class="cart__checkout-button button" name="checkout" form="cart">. The button lives OUTSIDE the form element and is linked by the form attribute, so a listener scoped to the form's subtree for clicks will miss it; listen for the form `submit` event (or document-level clicks on [name=checkout]).
  Source: https://raw.githubusercontent.com/Shopify/dawn/main/sections/main-cart-items.liquid
- **CK-06** [confirmed, design-critical, confidence high] Dawn cart drawer (snippets/cart-drawer.liquid): <form action="{{ routes.cart_url }}" id="CartDrawer-Form" class="cart__contents cart-drawer__form" method="post"> and <button type="submit" id="CartDrawer-Checkout" class="cart__checkout-button button" name="checkout" form="CartDrawer-Form">. The drawer snippet contains no additional_checkout_buttons / content_for_additional_checkout_buttons output.
  Source: https://raw.githubusercontent.com/Shopify/dawn/main/snippets/cart-drawer.liquid
- **CK-07** [confirmed, design-critical, confidence high] Dawn cart notification (snippets/cart-notification.liquid) has its own checkout path: a 'View cart' link to routes.cart_url, plus <form action="{{ routes.cart_url }}" method="post" id="cart-notification-form"> with <button class="button button--primary button--full-width" name="checkout">. Dawn's theme setting cart_type has options drawer, page, notification with notification as default, so all three surfaces must be covered.
  Source: https://raw.githubusercontent.com/Shopify/dawn/main/snippets/cart-notification.liquid
- **CK-08** [confirmed, design-critical, confidence high] Horizon (Shopify-authored theme source on GitHub): the cart form is <form action="{{ routes.cart_url }}" class="cart-form" id="cart-form" method="post"> in snippets/cart-products.liquid; the checkout button is <button type="submit" id="checkout" class="cart__checkout-button button" name="checkout" form="cart-form"> in snippets/cart-summary.liquid, which snippets/cart-drawer.liquid also renders, so page and drawer share one markup. Theme setting cart_type is page or drawer (default page).
  Source: https://raw.githubusercontent.com/Shopify/horizon/main/snippets/cart-summary.liquid
- **CK-09** [confirmed, confidence high] Product-page accelerated checkout ('Buy it now' / branded wallet) is emitted by the Liquid filter {{ form | payment_button }} inside {% form 'product', product %}. Documented output: <div data-shopify="payment-button" class="shopify-payment-button"> wrapping a <shopify-accelerated-checkout> custom element with attributes recommended, fallback, access-token, buyer-country, buyer-locale, buyer-currency, variant-params, shop-id, enabled-flags. `shopify-payment-button` survives only as a wrapper class name.
  Source: https://shopify.dev/docs/api/liquid/filters/payment_button
- **CK-10** [confirmed, confidence high] Cart accelerated checkout buttons are emitted with {% if additional_checkout_buttons %}{{ content_for_additional_checkout_buttons }}{% endif %} and render inside the custom element <shopify-accelerated-checkout-cart>. `additional_checkout_buttons` is a boolean that is true when the store has payment providers with offsite checkouts.
  Source: https://shopify.dev/docs/api/liquid/objects/additional_checkout_buttons
- **CK-11** [confirmed, design-critical, confidence high] Accelerated checkout buttons render as custom elements (shopify-accelerated-checkout on product pages, shopify-accelerated-checkout-cart on cart) with a CLOSED shadow DOM. The documentation read does not mention iframes for these buttons. Theme CSS/JS cannot reach the inner markup; only documented CSS custom properties (for example --shopify-accelerated-checkout-button-block-size) apply.
  Source: https://shopify.dev/docs/storefronts/themes/pricing-payments/accelerated-checkout
- **CK-12** [confirmed, design-critical, confidence high] The only documented JavaScript hook for accelerated buttons is click TRACKING via composed events on the host elements <shop-pay-wallet-button>, <shopify-amazon-pay-button>, <shopify-apple-pay-button>, <shopify-google-pay-button>, <shopify-paypal-button>. No documented API exists to cancel, replace or redirect the checkout these buttons start, so the middleware cannot rely on intercepting them.
  Source: https://shopify.dev/docs/storefronts/themes/pricing-payments/accelerated-checkout
- **CK-13** [confirmed, confidence high] Accelerated checkout buttons may be placed anywhere in a theme, including a cart drawer, and are re-rendered by the Section Rendering API when their section is requested. Any theme or app can therefore add them to drawer markup even though stock Dawn's drawer does not.
  Source: https://shopify.dev/docs/storefronts/themes/pricing-payments/accelerated-checkout
- **CK-14** [confirmed, design-critical, confidence high] Accelerated checkout buttons skip the cart entirely and send the buyer straight to the checkout of the store they are on (the vitrine), for a single variant. Unbranded buttons read 'Buy it now'; branded ones show Shop Pay, Apple Pay, Google Pay, Amazon Pay, PayPal, Venmo. Left enabled, they bypass the middleware and create orders on the vitrine store at vitrine prices.
  Source: https://help.shopify.com/en/manual/online-store/dynamic-checkout/dynamic-checkout
- **CK-15** [partially_correct, design-critical, confidence high] Documented way to turn them off on product pages: theme editor > Products template > Product information section > Buy buttons block > deselect 'Show accelerated checkout buttons' (same in Featured product sections). In Dawn source the block setting id is show_dynamic_checkout (checkbox, default true) guarding {{ form | payment_button }}. In Horizon the button is a separate block (blocks/accelerated-checkout.liquid).
  Source: https://help.shopify.com/en/manual/online-store/dynamic-checkout/add-buttons
  **CORRECTION:** Help Center steps and Dawn's `show_dynamic_checkout` (checkbox, default true, buy_buttons block) are confirmed. Horizon needs a sharper statement: the button is `{{ form_obj | payment_button }}` in blocks/accelerated-checkout.liquid, rendered from blocks/buy-buttons.liquid as a STATIC block (`"static": true`) with no settings. Static blocks "Cannot be removed or duplicated" but "Can be hidden and customized", so in Horizon the documented off-switch is hiding that block in the theme editor (or editing code), not removing it and not a 'Show accelerated checkout buttons' checkbox. (https://raw.githubusercontent.com/Shopify/horizon/main/blocks/buy-buttons.liquid)
- **CK-16** [confirmed, confidence high] Merchants can only show or hide all accelerated checkout buttons on product pages; individual wallets cannot be hidden. Which branded buttons appear depends on payment methods activated in payment settings; with none activated only the unbranded 'Buy it now' button shows. (Community risk flag, Shopify staff reply on community.shopify.dev thread 11641: no easy way to show only one wallet in cart.)
  Source: https://help.shopify.com/en/manual/online-store/dynamic-checkout/dynamic-checkout
- **CK-17** [confirmed, design-critical, confidence high] Turning off accelerated buttons on the CART is theme-specific and not covered by the Help Center pages read. Dawn renders them whenever `additional_checkout_buttons` is true (sections/main-cart-footer.liquid; no setting id containing checkout/accelerated/dynamic exists in Dawn's settings_schema.json), so removal needs a theme code edit. Horizon gates them with theme setting show_accelerated_checkout_buttons (checkbox, default true, Cart group).
  Source: https://raw.githubusercontent.com/Shopify/horizon/main/snippets/cart-summary.liquid
- **CK-18** [partially_correct, design-critical, confidence high] Shopify's own compatibility guidance lists apps that send customers to an external checkout, apps that interact with the cart, and currency converters as incompatible with accelerated checkout buttons, and states the buttons do not support cart attributes. This is Shopify's documented reason to disable them in a design like this one.
  Source: https://help.shopify.com/en/manual/online-store/dynamic-checkout/dynamic-checkout
  **CORRECTION:** Stated more strongly than the page. Shopify hedges: "Accelerated checkout buttons might conflict with certain apps" and such apps "might not be compatible with your online store" (currency converters, apps that interact with the cart, apps that take customers to an external checkout). The cart-attributes sentence is categorical and confirmed: "Accelerated checkout buttons don't support cart attributes." (https://help.shopify.com/en/manual/online-store/dynamic-checkout/dynamic-checkout)
- **PL-01** [confirmed, design-critical, confidence high] Cart permalink format: https://{shop}.myshopify.com/cart/{variant_id}:{quantity}[,{variant_id}:{quantity}...] using numeric variant IDs of the target (checkout) store. Documented example: https://{shop}.myshopify.com/cart/70881412:1,70881382:1. By default the link lands on checkout with the cart pre-loaded.
  Source: https://shopify.dev/docs/apps/build/checkout/create-cart-permalinks
- **PL-02** [confirmed, confidence high] Appending ?storefront=true makes the permalink land on the online store cart page instead of checkout.
  Source: https://shopify.dev/docs/apps/build/checkout/create-cart-permalinks
- **PL-03** [confirmed, design-critical, confidence medium] Line item properties in a permalink use the single query parameter `properties`, whose value is Base64 URL-encoded JSON (example {"engraving": "Hello world", "color": "red"} becomes eyJlbmdyYXZpbmciOiAiSGVsbG8gd29ybGQiLCAiY29sb3IiOiAicmVkIn0). They apply ONLY to the first product, maximum 25 properties. Multi-line carts with per-line properties cannot be represented by the fallback path.
  Source: https://shopify.dev/docs/apps/build/checkout/create-cart-permalinks
- **PL-04** [confirmed, confidence high] Supported checkout prefill parameters: checkout[email], checkout[shipping_address][first_name], [last_name], [address1], [address2], [city], [province], [country], [zip]. These are personal data placed in a URL query string, which the design should avoid.
  Source: https://shopify.dev/docs/apps/build/checkout/create-cart-permalinks
- **PL-05** [confirmed, confidence high] Discounts: ?discount={code}, multiple codes comma-separated (?discount={code},{code2}); codes that themselves contain a comma are not supported.
  Source: https://shopify.dev/docs/apps/build/checkout/create-cart-permalinks
- **PL-06** [confirmed, confidence high] `note` (?note=...) and cart attributes (?attributes[key]=value, repeatable) passed on a permalink reach the order and show in the Notes section of the order details page. This is the documented channel for carrying a middleware correlation ID or source-store tag on the fallback path.
  Source: https://shopify.dev/docs/apps/build/checkout/create-cart-permalinks
- **PL-07** [confirmed, confidence high] ?ref=... on a permalink is stored as the order's referral code and shown in the Conversion summary section. This matches Admin GraphQL CustomerVisit.referralCode, which supports URL attributes ref, source or r.
  Source: https://shopify.dev/docs/apps/build/checkout/create-cart-permalinks
- **PL-08** [confirmed, confidence high] Sales-channel attribution on a permalink uses ?access_token={storefront access token}; an optional &source_name={attribution definition handle} requires that access_token. Orders then show under that channel in Sales by Channel.
  Source: https://shopify.dev/docs/apps/build/checkout/create-cart-permalinks
- **PL-09** [confirmed, confidence high] ?payment=shop_pay sends the buyer into a Shop Pay checkout.
  Source: https://shopify.dev/docs/apps/build/checkout/create-cart-permalinks
- **PL-10** [confirmed, confidence high] Locale is expressed as a path prefix before /cart: https://{shop}.myshopify.com/fr/cart/70881412:1,70881382:1 yields a localized checkout. The permalink page documents no country, currency or Markets parameter.
  Source: https://shopify.dev/docs/apps/build/checkout/create-cart-permalinks
- **PL-11** [confirmed, design-critical, confidence high] The Limitations section lists exactly two items: selling plans (subscriptions) do not work with cart permalinks, and permalinks cannot bypass a storefront password. A password-protected checkout store therefore breaks the fallback path, and subscription lines must go through Storefront API cartCreate or be rejected.
  Source: https://shopify.dev/docs/apps/build/checkout/create-cart-permalinks
- **PL-12** [confirmed, confidence medium] For storefront URLs generally, Shopify documents a country deep-link query parameter with ISO 3166 two-letter codes (example.com?country=DE) to land a visitor in a given country/region context. It is not documented as a cart-permalink parameter; its effect on /cart/... links is untested here.
  Source: https://help.shopify.com/en/manual/international/managing-international-domains
- **PL-13** [confirmed, confidence medium] Shopify's agent-commerce docs show marketing parameters appended to a checkout-type cart URL of the Storefront cart form (/cart/c/{token}?key=...&utm_source=...) and describe query parameters as a way to attribute marketing campaigns. They do not state where the value is persisted on the order.
  Source: https://shopify.dev/docs/agents/carts-and-checkout.md
- **AT-01** [partially_correct, design-critical, confidence high] Order-level marketing attribution in Admin GraphQL 2026-10 is Order.customerJourneySummary (type CustomerJourneySummary) with fields customerOrderIndex, daysToConversion, firstVisit, lastVisit, moments, momentsCount, ready. - **AT-02** [partially_correct, confidence high] firstVisit/lastVisit are CustomerVisit objects with fields id, landingPage (URL), landingPageHtml, referrerUrl (URL), referralCode, referralInfoHtml, source, sourceDescription, sourceType (MarketingTactic), utmParameters (UTMParameters: campaign, content, medium, source, term), marketingEvent, occurredAt. - **AT-03** [confirmed, confidence high] UTM values on a CustomerVisit come from URL parameters (wording: of the referrer), and referrerUrl is the page where the buyer clicked the link into the store. - **AT-07** [confirmed, confidence high] Shopify sessions and visitors are cookie-based; a session ends after 30 minutes of inactivity; conversions use last-click attribution tied to the session where the conversion happened. - **AT-08** [confirmed, confidence high] The order's Conversion summary shows source/referrer, landing page, referral code and UTM parameters of the first visit when available, and is missing or limited when cookies are blocked, the order was a draft order, or the order did not come from the Online Store or Hydrogen channels with a captured source/landing page.

- **AT-09** [partially_correct, confidence high] Shopify stopped setting the _landing_page, _orig_referrer and _tracking_consent cookies on merchant storefronts starting September 15, 2025. ## Not documented by Shopify

- Semantics, lifetime and stability of the `token` field returned by GET /cart.js (it appears only inside the example JSON on the Ajax Cart reference).
- An explicit statement of price units on the Ajax Cart reference page itself (it only says presentment currency; 'currency's subunit' comes from the Liquid cart/line_item reference).
- Maximum number of cart lines, and size limits for line item properties, cart attributes and cart note in the Ajax Cart API (only Order.note 'up to 5000 characters' was seen, on the Admin GraphQL Order object).
- Whether the Ajax API is versioned or tied to an Admin/Storefront API version.
- A plain GET /checkout link as a supported way to leave the cart: the `routes` object has no checkout URL and the theme docs read describe only the POST cart form with a name="checkout" submitter.
- An exhaustive Shopify-published list of every path from an Online Store theme to checkout. The list in the claims is assembled from the cart template doc, the accelerated checkout doc, Theme Store requirements, and Dawn/Horizon source; third-party apps, checkout links shared from admin, and discount links were not enumerated.
- Any supported API to cancel, intercept or redirect an accelerated checkout button click (only click tracking on host custom elements is documented).
- iframe rendering of accelerated checkout buttons: the pages read describe only custom elements with a closed shadow DOM.
- A Help Center procedure or universal setting to hide accelerated checkout buttons on the cart page or cart drawer (product-page toggle is documented; cart is theme-specific).
- Cart permalinks: maximum number of variant:quantity pairs or URL length; whether the link replaces or merges with an existing cart on the target store; line item properties for any line other than the first; whether variants must be published to the Online Store channel; behaviour with Shopify Markets (country, currency, market-specific catalogs/prices).
- Whether utm_* parameters appended to a Storefront API cart.checkoutUrl or to a cart permalink are persisted into Order.customerJourneySummary (firstVisit/lastVisit.utmParameters). The practice is shown in Shopify docs, the persistence is not stated.
- What Shopify records as referrerUrl / landingPage when the buyer reaches the checkout store through a server-side redirect from an app proxy on another store.
- The Storefront API Cart reference states nothing about parameters that may be appended to checkoutUrl, nor about checkoutUrl lifetime (the cart guide only says it 'can be re-requested if it is stale').
- Domain scope (host-only versus parent-domain) of Shopify's own Online Store cookies: cart, cart_currency, localization, _shopify_essential, _shopify_analytics, _shopify_marketing, discount_code. The cookie policy lists names, purposes and durations only.
- Any mechanism for two different Shopify shops to share Shopify session, analytics, consent or cart cookies, even when both are on subdomains of one registrable domain. All same-root-domain guidance read concerns one shop's storefront and its own checkout.
- The Domain attribute applied by the Web Pixels browser.cookie.set, and whether browser.cookie.get can read HTTP-only cookies.
- Shopify-authored documentation on how fbclid/_fbp/_fbc, gclid/_gl, ttclid/_ttp are carried across domains or into checkout (only vendor documentation was found; Shopify's Meta/Google/TikTok channel-app help pages were not read in full).
- REST Admin Order properties landing_site / referring_site: their descriptions could not be located on the REST Order reference page fetched (REST is labelled legacy as of October 1, 2024); the GraphQL equivalents are documented.
- The current host/URL format of Online Store checkout pages: the 2017 changelog post 'Checkouts will occur at the shop domain instead of checkout.shopify.com' returned HTTP 404 on direct fetch and was seen only as a search snippet.
- Whether Shopify's Terms of Service / Acceptable Use Policy permit routing buyers from one store's storefront into another store's checkout. This was outside the assigned topic and was not checked; it should be confirmed on shopify.com/legal before building.

## Design implications

- Research caveat: all quotes were extracted through the WebFetch tool, which passes pages through a summarizing model. Wording was cross-checked with repeated fetches where marked high confidence, but exact strings (especially code and table rows) should be re-read on the live page before being treated as contractual.
- Intercept at the form level, not by element id: every documented checkout exit is a POST to the cart URL with a submitter named `checkout`. Listen for `submit` on document (capture phase) and test event.submitter name === 'checkout' and the form action against routes.cart_url. This covers Dawn (#cart, #CartDrawer-Form, #cart-notification-form), Horizon (#cart-form, shared by page and drawer) and {% form 'cart' %} (#cart_form). Buttons sit outside the form and are tied by the form attribute, so click listeners scoped inside the form miss them.
- Accelerated checkout buttons are the main bypass risk and cannot be intercepted (closed shadow DOM, no cancel API). They must be switched off on every vitrine: product pages via 'Show accelerated checkout buttons' in the Buy buttons block (Dawn setting id show_dynamic_checkout; Horizon: remove/hide the accelerated-checkout block), cart via Horizon's show_accelerated_checkout_buttons theme setting or by deleting the content_for_additional_checkout_buttons block in Dawn's main-cart-footer.liquid. Theme Store themes ship with both enabled by default, so add an onboarding check that fails if <shopify-accelerated-checkout> or <shopify-accelerated-checkout-cart> is present in rendered vitrine pages.
- If a bypass still happens, the order is created on the vitrine store at vitrine prices. The middleware should subscribe to orders/create on vitrine stores as a detector for leaked checkouts.
- Read the cart with fetch(window.Shopify.routes.root + 'cart.js') and send only items[].variant_id, items[].quantity, items[].properties and a flag for items[].selling_plan_allocation. Do not use items[].id as a line identifier, and never forward price fields: they are presentment-currency subunits of the vitrine market.
- Private cart attributes (double-underscore prefix) are invisible to /cart.js, so anything the middleware needs from the vitrine cart must be a normal attribute or a line item property (single-underscore properties are returned and are hidden at checkout).
- The permalink fallback is strictly weaker than cartCreate: properties only on the first line (max 25, Base64 URL-encoded JSON), no selling plans, blocked by a storefront password, no documented market/currency control. Decide per cart whether fallback is allowed: carts with subscriptions or per-line properties on more than one line should fail closed rather than silently lose data.
- A password-protected checkout store breaks permalinks. If the checkout store is meant to be non-browsable, hide it by other means (for example theme-level redirects) rather than the storefront password, or accept that only the Storefront API path works.
- Carry correlation and attribution explicitly, because no Shopify cookie or session is documented to cross between two shops. On the cartCreate path write cart attributes (middleware order key, vitrine shop, click IDs, UTM values); they surface in web pixel events as checkout.attributes and on the order. On the permalink path use attributes[...]=, note= and ref= (ref shows as referral code in Conversion summary).
- Also append utm_* (and, where used, fbclid/gclid/ttclid and the Google _gl value) to the final checkout URL so that the checkout store's first session has a meaningful landing URL. Treat native Shopify attribution on the checkout store as best-effort until verified with a test order, since persistence of UTMs from a checkout URL into customerJourneySummary is not stated in the docs.
- Expect the checkout store to report the vitrine domain (or nothing, after a server redirect) as referrer and the checkout URL as landing page; last-click reporting will otherwise show Direct. Read customerJourneySummary only after `ready` is true (up to 48 hours), with read_orders scope.
- Pixels belong on the checkout store. A custom pixel there runs in a sandboxed iframe and cannot see the top-frame URL by itself; read event.context.document.location and checkout.attributes and pass values to the vendor SDK explicitly. checkout_started can fire more than once per buyer on Checkout Extensibility shops, so de-duplicate using checkout.token.
- Consent is per domain: on different registrable domains the checkout store has no record of consent given on the vitrine, so pixels may not fire there in consent-required regions. Hosting vitrine and checkout on subdomains of one registrable domain lets vendor first-party cookies set at the parent domain (Google default behaviour; Meta/TikTok where configured at that level) be shared, but Shopify's own cookies are still not documented to be shared between two shops.
- Do not read _shopify_y, _shopify_s, _landing_page, _orig_referrer or _tracking_consent anywhere in the theme script or middleware; Shopify has announced their removal and points to Web Pixels clientId, browser APIs and the Customer Privacy API instead.
- Avoid the checkout[email] / checkout[shipping_address][...] permalink parameters: they put personal data in a URL that passes through redirects, logs and referrers.
- Pin Admin and Storefront API calls to 2026-10 (latest stable, supported to October 16, 2027); 2027-01 is the release candidate.

## Additional facts found by the verifier

- Consent CAN be carried from the vitrine into the checkout store's checkout on the cartCreate path. Storefront API `@inContext(visitorConsent: {analytics: true, preferences: true, marketing: false, saleOfData: false})` is "Supported from version `2025-10` and later" and "The consent information is automatically encoded and included in the resulting `checkoutUrl`". Design change: the theme script should read the buyer's consent on the vitrine (Customer Privacy API) and send it with the cart lines so the middleware can set visitorConsent on cartCreate; otherwise pixels on the checkout store stay suppressed in consent-required regions. Not available for cart permalinks.
  Source: https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/in-context.md
- Changelog (September 2, 2025, API 2025-10) confirms the mechanism: consent passed through `@inContext(visitorConsent)` is encoded into checkoutUrl through a `_cs` query parameter. Consequence: the middleware must not strip or rebuild the query string of checkoutUrl when appending its own parameters (use URL/searchParams to add, never replace).
  Source: https://shopify.dev/changelog/posts/incontext-directive-supports-visitor-consent-for-privacy-compliant-checkouts
- ScriptTag is not an option for delivering the theme script. Changelog dated August 24, 2026: "Starting October 1, 2026, the `scriptTagCreate` and `scriptTagUpdate` mutations will return an user error" and "On March 1, 2027, Shopify will stop injecting script tags into storefronts". Documented replacement is an app embed block in a theme app extension, which the merchant must switch on in the theme editor ("App users activate app embed blocks in the theme editor"); the alternative is a manual theme code edit per vitrine. The onboarding flow needs a step (and a health check) for this activation on every vitrine theme, including after theme changes.
  Source: https://shopify.dev/changelog/online-store-script-tags-deprecation
- Legal constraint the researcher left unchecked. Shopify Terms of Service (last updated August 1, 2026) section 4.5: "You agree to use Shopify Checkout for any sales associated with your online store." Section 2.1 also says a Store Owner may have multiple Shopify Stores. The design does end in Shopify Checkout, but on a different store than the one whose storefront made the sale; the ToS text read does not say whether that satisfies 4.5 for the vitrine store. The Acceptable Use Policy and the payment provider's own terms (for example Shopify Payments terms on which store/URL may sell the goods being charged) were not found to address it explicitly and should be confirmed with Shopify before building.
  Source: https://www.shopify.com/legal/terms
- Shopify API License and Terms of Use (last updated February 27, 2026) section 2.3.18: developers may not, without Shopify's express written authorization, "use an alternative to Shopify Checkout for checkout or payment processing for Shopify Merchants"; section 2.3.20: "Custom Applications may not be installed by more than one Merchant." The definitions add "a Merchant may have more than one Merchant Store". The middleware uses Shopify Checkout, so (i) is not obviously triggered, but the clause is the one Shopify would apply to checkout-redirect apps; keep every app strictly inside the one merchant's own stores. Sub-item (ii) of 2.3.18 restricts how Shopify Checkout may be embedded; its exact wording could not be extracted and should be read directly.
  Source: https://www.shopify.com/legal/api-terms
- Intercepting the checkout submit skips the native POST to /cart, which is what normally saves the form's fields. The cart template doc ties note and attribute inputs to the form (`<textarea name="note" form="cart">`, `name="attributes[attribute-name]" form="cart"`) so they are sent with the submit. If the theme script calls preventDefault and then reads /cart.js, any note, attribute or quantity edit that the theme has not already saved via Ajax is lost. The script should first POST the form's note/attributes/updates to cart/update.js (response is the cart JSON) and use that response as the payload. (The data-loss consequence is an inference from the documented form mechanics.)
  Source: https://shopify.dev/docs/storefronts/themes/architecture/templates/cart
- Horizon's accelerated checkout on product pages has no checkbox. blocks/buy-buttons.liquid renders `{% content_for 'block', type: 'accelerated-checkout', id: 'accelerated-checkout', ... %}` as a static block, and static blocks "Cannot be removed or duplicated" but "Can be hidden and customized". The Help Center procedure ('Show accelerated checkout buttons' checkbox in the Buy buttons block) therefore does not map onto Horizon; the onboarding instructions must be theme-specific (Dawn: show_dynamic_checkout; Horizon: hide the static Accelerated checkout block, plus theme setting show_accelerated_checkout_buttons for the cart).
  Source: https://shopify.dev/docs/storefronts/themes/architecture/blocks/theme-blocks/static-blocks
- Horizon's snippets/cart-summary.liquid contains a second cart form besides #cart-form: `{% form 'cart', cart %}{{ form | payment_terms }}{% endform %}` (renders id="cart_form", class="shopify-cart-form", action="/cart"). It has no checkout submitter. An interceptor that matches only on form action = cart URL would catch it; the match must require event.submitter with name="checkout" as well.
  Source: https://raw.githubusercontent.com/Shopify/horizon/main/snippets/cart-summary.liquid
- For the server-side cartCreate call the cart guide requires a buyer IP header: "you must include the `Shopify-Storefront-Buyer-IP` header in your Storefront API call when making server side requests" (stated for preserving the logged-in checkout experience), and says "the checkoutUrl should be requested when the buyer is ready to navigate to checkout and can be re-requested if it is stale". The middleware should forward the buyer's IP from the app proxy request and must not cache checkoutUrl. The same page does not say whether cart-level attributes reach the checkout or order.
  Source: https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/cart/manage
- The Help Center cart-permalink page documents one more parameter than the developer page, `channel=buy_button` (attributes the order to the Buy Button channel), and an admin 'Create checkout link' action on product pages when the Buy Button channel is installed. Neither page mentions utm, currency or market parameters. Admin-created checkout links on a vitrine store are another checkout path that bypasses the middleware.
  Source: https://help.shopify.com/en/manual/checkout-settings/cart-permalink
- Ajax error bodies are not uniform, which matters if the theme script parses them: cart/change.js for a line not in the cart returns HTTP 400 with `{"status":"bad_request","message":"no valid id or line parameter",...}` (status is a string), while add/update errors use numeric status (422 or 404 with message "Cart Error"). When quantity exceeds stock on add, the doc says "the cart will instead add the maximum available quantity", so the vitrine cart quantity can already differ from what the buyer asked for; the checkout store must re-validate stock independently.
