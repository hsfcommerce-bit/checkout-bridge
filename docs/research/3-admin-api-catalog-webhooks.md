- **AC-61** [confirmed, design-critical, confidence high] HMAC verification procedure: compute HMAC-SHA256 over the RAW request body (before any JSON body parser touches it) using the app's client secret as the key, base64-encode it, and compare with the value of the X-Shopify-Hmac-SHA256 header using a timing-safe comparison; on mismatch the sample code responds 401. With one Dev Dashboard app per store, the secret is that store's app client_secret, selected by X-Shopify-Shop-Domain.
  Source: https://shopify.dev/docs/apps/build/webhooks/verify-deliveries
- **AC-62** [confirmed, design-critical, confidence high] After rotating the app's client secret it can take up to an hour before webhook HMAC digests are generated with the new secret, so the verifier must accept both old and new secrets during rotation.
  Source: https://shopify.dev/docs/apps/build/webhooks/subscribe/https
- **AC-63** [confirmed, design-critical, confidence high] Response requirement: reply 200 OK (any 2xx is success in the troubleshooting page); anything outside the 200 range, including 3XX redirects, is treated as a failure. Shopify applies a one-second connection timeout and a five-second timeout for the whole request, and verifies the endpoint's SSL certificate. The guidance is to enqueue the payload and process asynchronously.
  Source: https://shopify.dev/docs/apps/build/webhooks/subscribe/https
- **AC-64** [confirmed, design-critical, confidence high] Retry policy: on no response or an error Shopify retries 8 times over the next 4 hours. ## Design implications

- Pin every Admin and Storefront call to 2026-10 in the URL and track the version per store; versions fall forward silently after ~12 months, so schedule a quarterly review (2027-01 is already the release candidate).
- Variant matching by barcode must change now: ProductVariant.barcode is deprecated in 2026-10 and returns only the first of up to 20 barcodes. Sync the `barcodes` connection (value + type) and index every value; treat SKU as case-sensitive; keep selectedOptions (name/value) as the third matching key.
- Never forward or trust vitrine prices: ProductVariant.price is in the checkout shop's default currency (Shop.currencyCode). If the mapping table stores prices for display or sanity checks, store contextualPricing(context: {country}) price as MoneyV2 with its currency code, and remember the actual charge is whatever the checkout store's Storefront cart computes.
- Visibility gate for the mapping table must be a conjunction, not a single flag: product.status is ACTIVE (or UNLISTED), product publishedOnPublication(publicationId) is true for the publication the Storefront token reads, the variant itself is published to that publication (variant-level publishing exists since 2026-07), and any scheduled publishDate is in the past (ResourcePublication.isPublished is true for scheduled items). Otherwise cartCreate will reject lines for variants that look valid in Admin.
- Request these Admin scopes on the checkout-store app: read_products, read_inventory, read_publications (write_publications only if the middleware will auto-publish with publishablePublish), read_markets only if Market objects are listed; plus the unauthenticated_* scopes as REQUIRED scopes (unauthenticated_read_product_listings, unauthenticated_write_checkouts, unauthenticated_read_checkouts, optionally unauthenticated_read_product_inventory) before creating the storefront access token. The vitrine-store app needs only read_products (+ read_inventory if stock is mirrored).
- Create exactly one storefront access token per checkout store, persist it encrypted, and on startup list Shop.storefrontAccessTokens to reuse or clean up by title — the limit is 100 active tokens and no expiry is documented. If scopes change, create a new token (tokens inherit scopes at creation) and delete the old one.
- Admin tokens from the client credentials grant last 24 hours (expires_in 86399): cache per store and refresh before expiry; treat an in-body ACCESS_DENIED as a signal to re-mint.
- Initial and periodic full catalog sync should use bulkOperationRunQuery (products -> variants is one nested connection; stay within 5 connections / 2 nesting levels; up to 5 concurrent bulk queries per app per shop on 2026-01+). Poll with bulkOperation(id:) or subscribe to bulk_operations/finish, download the JSONL within 7 days, and rebuild parent/child links from __parentId. Bulk execution does not consume the cost bucket.
- Incremental sync by pagination: page size <= 250, keep requested cost under 1,000 points per query, read extensions.cost.throttleStatus on every response and sleep when currentlyAvailable is below the next query's requested cost; handle errors[].extensions.code == THROTTLED on HTTP 200 with a ~1 second backoff. Do not hard-code bucket sizes; Standard plans restore only 100 points/second.
- Webhook endpoint design: capture the raw body bytes before JSON parsing, look up the client_secret by X-Shopify-Shop-Domain (one Dev Dashboard app per store means one secret per store), compute base64(HMAC-SHA256(secret, rawBody)), compare timing-safely with X-Shopify-Hmac-Sha256 (case-insensitive header lookup), reject with 401 on mismatch, then enqueue and return 200 within 5 seconds (1 second connect). Keep the previous secret valid for at least an hour after rotation.
- Deduplicate on X-Shopify-Webhook-Id, order by X-Shopify-Triggered-At / payload updated_at, and treat every product webhook as an invalidation signal: refetch the product and its variants through GraphQL rather than parsing the REST-shaped payload (payloads may carry only the first 100 variants per a staff community post, and do not carry the new barcodes list or publication state).
- Subscription strategy: if subscribing per shop with webhookSubscriptionCreate, Shopify deletes the subscription after 8 consecutive failures (retries span 4 hours) — add a startup/daily check that lists webhookSubscriptions and recreates missing ones. App-configuration (TOML + shopify app deploy) subscriptions are not deleted on failure and are the more robust choice when each store has its own Dev Dashboard app.
- Subscribe at minimum to products/create, products/update, products/delete, inventory_levels/update (maintain an inventory_item_id -> variant index because the payload has no variant ID), app/uninstalled (purge tokens and mapping for that store), shop/update (currency/domain changes) and app/scopes_update; consider product_publications/* or product_listings/* on the checkout store so unpublish events invalidate mappings.
- Because webhook delivery and ordering are not guaranteed, run a reconciliation job (products query filtered by updated_at, or a nightly bulk operation) and make the Checkout click path tolerant: on cartCreate userErrors for a mapped variant, mark the mapping stale, trigger a refetch, and fall back to the cart permalink.
- products/update also fires when a product is ordered, so volume scales with order count; debounce refetches per product ID and consider include_fields / filter on the subscription to cut load.
- Compliance webhooks: the documented obligation is for App Store-distributed apps; for same-organization Dev Dashboard apps it is undocumented either way. Cheap mitigation: implement the three endpoints (HMAC check, 401 on invalid, 200 otherwise) since the middleware stores no customer data.

## Additional facts found by the verifier

- DESIGN-CRITICAL: the Storefront reference distinguishes token types by where the call originates. Public tokens (X-Shopify-Storefront-Access-Token, from storefrontAccessTokenCreate) are for browser/mobile clients and their capacity scales by buyer IP. Private tokens (Shopify-Storefront-Private-Token) are for server contexts, and for buyer-driven requests the server must also send Shopify-Storefront-Buyer-IP (documented as case-sensitive); omitting it can lead to throttled requests, limited bot protection and unauthenticated flows at checkout. Because the middleware calls cartCreate from one server IP, the documented fit is a private token plus the buyer's IP forwarded from the app-proxy request, not a public token. Documented ways to get a private token: the Headless channel, a delegate access token, or unauthenticated scopes on an existing access token.
  Source: https://shopify.dev/docs/api/storefront/latest
- Storefront API rate limiting relevant to the redirect step: real buyer traffic has no fixed limit, bots/crawlers are limited, checkout creation is throttled per minute and reported as a Throttled error inside an HTTP 200, and suspicious requests get a 430 Shopify Security Rejection. The middleware needs explicit handling for both (retry/backoff, then fall back to the cart permalink).
  Source: https://shopify.dev/docs/api/storefront/latest
- Tokenless Storefront access is documented to cover products, collections, search and cart read/write (query complexity limit 1,000) but not product tags, metafields, metaobjects, menus or customers. cartCreate therefore has a documented path that needs no storefront access token and no unauthenticated_* scopes - a useful fallback if storefrontAccessTokenCreate returns ACCESS_DENIED. Which publication tokenless requests read from is not documented.
  Source: https://shopify.dev/docs/api/storefront/latest
- The webhookSubscriptions query returns only shop-scoped (API-created) subscriptions, not app-scoped subscriptions declared in TOML. The proposed startup/daily 'list and recreate missing subscriptions' check works only for subscriptions created with webhookSubscriptionCreate; TOML subscriptions are visible only in the Dev Dashboard (Versions > Configuration) and in delivery logs.
  Source: https://shopify.dev/docs/api/admin-graphql/latest/objects/webhooksubscription
- Contrary to the researcher's not_documented list, warnings before deletion ARE documented: "Warning emails are sent to the app's emergency developer email address." (shopify.dev, HTTPS webhook delivery guide). Make sure each per-store Dev Dashboard app has a monitored emergency developer email.
  Source: https://shopify.dev/docs/apps/build/webhooks/subscribe/https
- There is no webhook for variant-level publish/unpublish yet: the variant-publishing changelog says variant_publication create/update/delete webhooks are still under development (product feed webhooks fire a product update instead). Variant visibility on the checkout store must be reconciled by polling ProductVariant.publishedOnPublication, not by events.
  Source: https://shopify.dev/changelog/publish-and-unpublish-product-variants-independently-from-product
- UNLISTED has two extra documented constraints: it is returned by the Storefront API and Liquid only when the product is referenced individually by handle, id or metafield reference, and the status is only visible from API 2025-10 upward (older versions report it as active). Keep both stores' Admin calls on 2025-10 or later so UNLISTED is not silently read as ACTIVE.
  Source: https://shopify.dev/docs/api/admin-graphql/latest/enums/ProductStatus
- Barcode changelog details that settle two of the researcher's open items: the `barcode` search filter on products and productVariants now matches any barcode on a variant; writing the deprecated `barcode` field updates only the first entry and leaves the others untouched; BarcodeType values are UPC, EAN, ISBN, GTIN and ASIN, and an undeclared type means the value is stored exactly as sent. New `barcodes` inputs exist on productSet, productVariantsBulkCreate and productVariantsBulkUpdate.
  Source: https://shopify.dev/changelog/product-variant-barcode-is-being-replaced-by-barcodes
- If the design uses include_fields to shrink products/update payloads (as one design implication suggests), Shopify drops later deliveries whose payload is identical to a recent one. The documented remedy is to include an always-changing field such as updated_at in include_fields; otherwise distinct updates can be silently lost.
  Source: https://shopify.dev/docs/apps/build/webhooks/customize/modify-payloads
- 2026-10 adds an optional channelId argument to the Storefront API @inContext directive, applying a sales channel's context (availability and pricing) to a query. This is a documented lever for the open question of which publication a Storefront request reads from. Also, when @inContext is omitted the primary market is used, so prices on the created cart default to the checkout store's primary market unless country context is passed.
  Source: https://shopify.dev/changelog/release-notes/2026-10
- Client credentials grant prerequisites beyond 'same organization': the app must be created in the Dev Dashboard, installed on the target store, and the scopes must be selected on a released app version. The token request carries no scopes - the `scope` field in the response is a readback of the version's scopes - and adding a scope requires releasing a new version and approving the change on the store. Cross-organization use fails with the error shop_not_permitted. The middleware should compare the returned `scope` against the scopes it needs after every token mint.
  Source: https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens/client-credentials-grant
- Shopify has a newer subscription mechanism called Events (announced May 27, 2026 as developer preview): declared only in shopify.app.toml under [events], field-level triggers and custom GraphQL payloads, Product and Customer topics first, Shopify CLI 3.92+, and delivery headers without the X- prefix (Shopify-Topic, Shopify-Action, Shopify-Hmac-Sha256, Shopify-Webhook-Id, Shopify-Triggered-At, Shopify-Shop-Domain). Webhooks remain fully supported and are still the only option for API-managed subscriptions, so build on webhooks now, but keep the header parser and verifier tolerant of both naming schemes.
  Source: https://shopify.dev/changelog/next-generation-events-now-available-in-developer-preview
- For catalogs above 25,000 objects the pagination guide's documented options are narrowing with filters or running a bulk query operation; paginating the whole products/productVariants connection past the cap is not supported. An updated_at-filtered incremental query stays under the cap; full syncs of large catalogs must use bulkOperationRunQuery. Bulk result files stay available for seven days and the bulk query needs the same scopes as the equivalent normal query (ACCESS_DENIED error code otherwise).
  Source: https://shopify.dev/docs/api/usage/pagination-graphql
- RISK FLAG (community, not primary): in the same thread used for AC-68, later posts from February-March 2026 report production products/update payloads containing full variant data for up to 250 variants while other environments cut off at 100. The truncation threshold is therefore not reliable in either direction - a handler must treat the variants array as possibly incomplete and refetch via GraphQL (variantsCount / variants connection).
  Source: https://community.shopify.dev/t/question-about-products-update-webhook-after-increasing-product-variants-to-2048/22855
