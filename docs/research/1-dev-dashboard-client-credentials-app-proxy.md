# Dev Dashboard apps, client credentials grant, App Proxy (Shopify docs as read on 2026-10-05)

Researched on 2026-10-05 from Shopify primary documentation. Each claim was re-checked by an independent verifier;
the verdict is shown in brackets. "CORRECTION" lines override the claim they follow. Items marked community/RISK are not official.

## Claims

- **SC-00** [confirmed, confidence high] The latest stable API version is 2026-10 (released October 1, 2026, accessible until October 16, 2027 15:00 UTC). 2027-01 is the release candidate. 2026-01, 2026-04 and 2026-07 are still 'Stable'; 2025-10 and older are listed as 'Unsupported'.
  Source: https://shopify.dev/docs/api/usage/versioning
- **SC-00b** [confirmed, confidence high] The client-credentials tutorial sample still hard-codes Admin API version 2025-01 in its example URL, which is no longer in the supported table. Do not copy the version from the sample; requests to an inaccessible version fall forward to the oldest accessible stable version.
  Source: https://shopify.dev/docs/api/usage/versioning
- **SC-01** [confirmed, confidence high] App creation in the Dev Dashboard: Apps (left nav) > Create app (top right) > 'Start from Dev Dashboard' > name the app > Create. Shopify positions this path for API-only/automation apps; the CLI path is recommended for apps with extensions.
  Source: https://shopify.dev/docs/apps/build/dev-dashboard/create-apps-using-dev-dashboard
- **SC-02** [confirmed, confidence high] A merchant reaches the Dev Dashboard of their own (merchant) organization from the store admin: Settings > Apps > Develop apps > Build apps in Dev Dashboard, then Create app. Custom apps are now created and managed only there.
  Source: https://help.shopify.com/en/manual/apps/app-types/custom-apps
- **SC-03** [confirmed, confidence high] A version is a snapshot of the app's configuration, URLs and settings. At least one released version is required before the app can be installed on any store.
  Source: https://shopify.dev/docs/apps/build/dev-dashboard/create-apps-using-dev-dashboard
- **SC-04** [confirmed, confidence high] The Dev Dashboard tutorial documents exactly three version fields: App URL, Webhooks API version ('Typically the newest version') and Scopes; then 'Release'. For a non-embedded app the App URL may be the default https://shopify.dev/apps/default-app-home.
  Source: https://shopify.dev/docs/apps/build/dev-dashboard/create-apps-using-dev-dashboard
- **SC-05** [confirmed, confidence medium] The full documented configuration surface of an app version is the shopify.app.toml reference: name, client_id, application_url, embedded, handle; [access_scopes] scopes / optional_scopes / use_legacy_install_flow; [auth] redirect_urls; [webhooks] api_version (+ [[webhooks.subscriptions]] topics, uri, filter, include_fields, compliance_topics); [app_proxy] url / subpath / prefix; [pos] embedded; [app_preferences] url; [access.admin]; [customer_authentication]; [events]. The docs say many (not necessarily all) of these can also be set in the Dev Dashboard UI; a per-field list of the UI is not documented.
  Source: https://shopify.dev/docs/apps/build/cli-for-apps/app-configuration
- **SC-06** [confirmed, confidence high] [auth] redirect_urls are only used by the authorization code grant; they are irrelevant for the client credentials grant. They are mandatory only 'before making your app public'.
  Source: https://shopify.dev/docs/apps/build/cli-for-apps/app-configuration
- **SC-07** [confirmed, confidence high] [webhooks] api_version is a per-app-version setting that controls the API version used to serialize webhook payloads; it is required in the TOML.
  Source: https://shopify.dev/docs/apps/build/cli-for-apps/app-configuration
- **SC-08** [confirmed, design-critical, confidence high] Some app settings live outside the version/TOML in the Dev Dashboard app Settings: client ID and client secrets, icon, contact email, App Automation Tokens, EventBridge destination. Credentials are under Apps > app > Settings > Credentials.
  Source: https://shopify.dev/docs/apps/build/authentication-authorization/client-credentials-grant
- **SC-09** [confirmed, confidence high] Installation: open the app in the Dev Dashboard, click 'Install app' on the Installs card (or the three-dot menu in the Apps list); an install link opens the OAuth/consent flow in a new tab; select the store; click Install.
  Source: https://shopify.dev/docs/apps/build/dev-dashboard/create-apps-using-dev-dashboard
- **SC-10** [confirmed, design-critical, confidence high] One Dev Dashboard custom app can be installed on several stores, but only stores that are part of the same organization as the app. It cannot be shared to stores in a different organization (even ones the same person owns).
  Source: https://help.shopify.com/en/manual/apps/install-setup-apps
- **SC-11** [confirmed, design-critical, confidence high] The same help page states the cross-organization prohibition explicitly, and says the install link can be shared for other stores in the same organization; in the install step a multi-store user picks the target store.
  Source: https://help.shopify.com/en/manual/apps/install-setup-apps
- **SC-12** [partially_correct, design-critical, confidence high] To reach a store outside the app's organization the documented route is 'custom distribution' (irreversible choice): install link bound to one store domain, or multiple stores only if they belong to the same Plus organization. Such installs must use authorization code grant or token exchange, not client credentials.
  Source: https://shopify.dev/docs/apps/launch/distribution
  **CORRECTION:** Correct, but the quoted cell is truncated: it continues "or on transfer-disabled development stores". The page does not literally say "not client credentials"; it lists token exchange (embedded) or authorization code grant (not embedded) and points to "choosing an approach". The exclusion of client credentials comes from the client-credentials page. Whether a merchant-organization Dev Dashboard app shows the Distribution card is not documented. (https://shopify.dev/docs/apps/launch/distribution)
- **SC-13** [confirmed, design-critical, confidence high] For non-Plus merchants an 'organization' is a group of stores with shared users and centralized settings/billing. Stores are not automatically in one organization: the owner must group them. Requirements: at least two stores, the same store owner on all of them, same billing currency (INR excluded). No specific limit on number of stores for non-Plus.
  Source: https://help.shopify.com/en/manual/your-account/manage-orgs-and-stores/manage-orgs/group-store
- **SC-14** [confirmed, design-critical, confidence high] Grouping path: store admin > Settings > General > Transfer store > Manage > 'Move store into a new or existing organization' > select or create organization > Confirm. Only the store owner sees this option; Plus stores use expansion stores instead.
  Source: https://help.shopify.com/en/manual/your-account/manage-orgs-and-stores/manage-orgs/group-store
- **SC-15** [confirmed, confidence high] Side effects of grouping stores into an organization: billing/payment methods are consolidated at organization level, billing and user-management permissions move to the organization owner, and the organization's billing currency can never be changed. A store can later be removed by the organization owner.
  Source: https://help.shopify.com/en/manual/your-account/manage-orgs-and-stores/manage-orgs/group-store
- **SC-16** [partially_correct, design-critical, confidence high] For client-credentials purposes 'same organization' is defined operationally: the app and the store must both be listed under the same org in the Dev Dashboard (check the org id in dev.shopify.com/dashboard/<org-id>). Owning a store, or having the app installed on it, is not sufficient.
  Source: https://shopify.dev/docs/apps/build/authentication-authorization/client-credentials-grant
  **CORRECTION:** Substance confirmed ("If the store isn't listed, it's not in this organization."), but the documented check is narrower than stated: step 2 literally says "Click Dev stores in the sidebar and confirm your target store appears in the list." The docs do not say where a merchant organization's live stores are listed in the Dev Dashboard, so the check for production stores is not documented. Help Center separately confirms merchant custom apps use the client credentials grant. (https://shopify.dev/docs/apps/build/authentication-authorization/client-credentials-grant)
- **SC-17** [confirmed, confidence high] Who can use the Dev Dashboard on the merchant side: store owners automatically; staff need the 'App development > Develop' permission (App developer role). Collaborator accounts cannot access the Dev Dashboard.
  Source: https://help.shopify.com/en/manual/apps/app-types/custom-apps
- **SC-18** [confirmed, confidence high] Legacy (admin-created) custom apps: announced October 30, 2025; since January 1, 2026 new ones cannot be created in the Shopify admin. New custom apps must be built in the Dev Dashboard and then installed.
  Source: https://changelog.shopify.com/posts/legacy-custom-apps-can-t-be-created-after-january-1-2026
- **SC-19** [confirmed, confidence high] Existing legacy custom apps keep working and are still managed from the Shopify admin; no sunset/shutdown date for existing legacy apps is published on the pages read. Their Admin API token is revealed only once, and their key/secret cannot be rotated.
  Source: https://changelog.shopify.com/posts/legacy-custom-apps-can-t-be-created-after-january-1-2026
- **SC-19b** [confirmed, confidence high] Developer docs confirm the same status for admin-created apps and add that their credentials cannot be rotated; new apps should use Dev Dashboard or CLI.
  Source: https://shopify.dev/docs/apps/build/authentication-authorization/legacy/admin-custom-apps
- **SC-20** [confirmed, design-critical, confidence high] Client credentials token endpoint: POST https://{shop}.myshopify.com/admin/oauth/access_token with header Content-Type: application/x-www-form-urlencoded and body parameters grant_type=client_credentials, client_id, client_secret. {shop} is the myshopify.com subdomain. No scope parameter is sent.
  Source: https://shopify.dev/docs/apps/build/authentication-authorization/client-credentials-grant
- **SC-21** [confirmed, design-critical, confidence high] Response JSON has exactly three documented fields: access_token (string), scope (granted scopes), expires_in (integer seconds). Documented example: {"access_token":"f85632530bf277ec9ac6f649fc327f17","scope":"read_products","expires_in":86399}. No refresh_token is returned.
  Source: https://shopify.dev/docs/apps/build/authentication-authorization/client-credentials-grant
- **SC-22** [confirmed, design-critical, confidence high] Token lifetime is 24 hours; renewal is done by repeating the same client-credentials request (there is no refresh-token flow). The official sample caches the token and renews 60 seconds before expiry.
  Source: https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens
- **SC-23** [confirmed, design-critical, confidence high] Same-organization restriction: the grant only works when the app and the target store belong to the same Shopify organization; preconditions are that the app has a released version with scopes and is installed on the store.
  Source: https://shopify.dev/docs/apps/build/authentication-authorization/client-credentials-grant
- **SC-24** [confirmed, design-critical, confidence high] Documented error when app and store are in different organizations: error code shop_not_permitted with the message below. The HTTP status code for this error is not documented (the sample only throws on a non-OK response.status).
  Source: https://shopify.dev/docs/apps/build/authentication-authorization/client-credentials-grant
- **SC-25** [confirmed, design-critical, confidence high] Second documented error: 'Invalid API key or access token' occurs when client_id/client_secret are sent directly to the Admin API. The exchanged token must be sent in the X-Shopify-Access-Token header.
  Source: https://shopify.dev/docs/apps/build/authentication-authorization/client-credentials-grant
- **SC-26** [confirmed, design-critical, confidence high] Scopes are never requested in the token call; the 'scope' field in the response reports what is configured on the app's released version (and granted on the store). The middleware should compare this readback against the scopes it needs on every token fetch.
  Source: https://shopify.dev/docs/apps/build/authentication-authorization/client-credentials-grant
- **SC-27** [confirmed, design-critical, confidence high] Scope changes require releasing a new app version AND approving the change on each store where the app is installed; they are not applied automatically.
  Source: https://shopify.dev/docs/apps/build/dev-dashboard/create-apps-using-dev-dashboard
- **SC-28** [confirmed, design-critical, confidence medium] Docs are internally inconsistent on who approves a scope change for own-organization apps: the manage-access-scopes page says you approve it yourself at release with no merchant consent step, while the Dev Dashboard tutorial says manual approval in the Shopify admin is still needed. Treat approval per store as required until verified, and check the 'scope' readback.
  Source: https://shopify.dev/docs/apps/build/authentication-authorization/app-installation/manage-access-scopes
- **SC-29** [confirmed, confidence high] Actually granted scopes can be verified with the Admin GraphQL query currentAppInstallation { accessScopes { handle } }; a declared scope is not necessarily granted.
  Source: https://shopify.dev/docs/api/usage/access-scopes
- **SC-30** [confirmed, design-critical, confidence high] For stores outside the app's organization, client credentials cannot be used at all; Shopify directs you to custom distribution plus authorization code grant (non-embedded) or token exchange (embedded).
  Source: https://shopify.dev/docs/apps/build/authentication-authorization/client-credentials-grant
- **SC-31** [confirmed, design-critical, confidence high] Client secret rotation (Dev Dashboard > Apps > app > Settings > Credentials > Rotate): old and new secret are both active until the old is revoked; every access token is pinned to the secret that minted it, so tokens must be re-minted with the new secret before revoking the old one.
  Source: https://shopify.dev/docs/apps/build/authentication-authorization/client-secrets/rotate-revoke-client-credentials
- **SC-32** [confirmed, design-critical, confidence medium] During rotation webhooks are signed with the oldest unrevoked client secret. Which secret signs app proxy requests during rotation is not documented; verify proxy signatures against all unrevoked secrets.
  Source: https://shopify.dev/docs/apps/build/authentication-authorization/client-secrets/rotate-revoke-client-credentials
- **RISK-01** [partially_correct, design-critical, confidence medium] COMMUNITY (not primary; Shopify staff 'Donal-Shopify', Dec 2025): an app created in a Partner organization cannot use client credentials on a merchant's production store even if the same person owns both. Implication: create the app in the merchant organization's Dev Dashboard (opened from the store admin), not in a Partner org.
  Source: https://community.shopify.dev/t/custom-app-credentials/27460
  **CORRECTION:** COMMUNITY. Substance confirmed but the quote is a paraphrase. Donal-Shopify (Dec 23, 2025) wrote: "Partner apps can't use it on merchant stores (even your own merchant store)". He recommended the authorization code grant, not creating the app in the merchant organization; that implication is supported instead by the Help Center (primary), which says merchant Dev Dashboard custom apps use the client credentials grant. (https://community.shopify.dev/t/custom-app-credentials/27460)
- **SC-40** [confirmed, design-critical, confidence high] App proxy is configured in shopify.app.toml under [app_proxy] with three keys, all required if the section is present: url, prefix, subpath (example: url = "/my-app-proxy", prefix = "apps", subpath = "my-custom-path"), deployed with `shopify app deploy`. An app can have only one proxy route.
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies
- **SC-41** [confirmed, confidence high] App proxy can alternatively be configured in the Dev Dashboard UI when creating a version (Apps > app > Versions > Create a version > App proxy); Shopify recommends file-based configuration via CLI.
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies
- **SC-42** [confirmed, confidence high] `shopify app deploy` builds the app, creates an app version (snapshot of config + extensions) and releases it; --no-release creates without releasing; --allow-updates is for CI. A Dev Dashboard-created app can be bound to a local TOML with `shopify app config link` (--client-id).
  Source: https://shopify.dev/docs/api/shopify-cli/app/app-config-link
- **SC-43** [confirmed, design-critical, confidence high] Allowed prefix values are exactly: a, apps, community, tools.
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies
- **SC-44** [confirmed, design-critical, confidence high] subpath: letters, numbers, underscores, hyphens; max 30 characters; reserved values admin, services, password, login are forbidden.
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies
- **SC-45** [confirmed, confidence high] url may be relative (Shopify prepends application_url on dev/deploy) or an absolute URL of the proxy endpoint. Storefront https://<shop_url>/<prefix>/<subpath>[/child] maps to <proxy url>[/child].
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies
- **SC-46** [partially_correct, design-critical, confidence high] Changing the proxy `url` in a new version takes effect immediately on all installed stores, but changes to `prefix`/`subpath` apply only to new installations (existing stores need a manual change in admin or uninstall/reinstall).
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies
  **CORRECTION:** The two rules are confirmed verbatim. The remediation sentence is written only for dev stores: "To change the proxied path on a dev store that already has the app installed, either change it in your dev store admin, or uninstall and reinstall the app." Applying it to live stores is an extrapolation (consistent with the documented per-store Customize URL setting). (https://shopify.dev/docs/apps/build/online-store/app-proxies)
- **SC-47** [confirmed, confidence high] The proxy path is merchant-editable per store (Settings > Apps > app > App Proxy URL > Customize URL), so the theme script must use the path actually configured on that store, and the backend should read path_prefix rather than assume the configured value.
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies/authenticate-app-proxies
- **SC-48** [confirmed, design-critical, confidence high] The docs require the write_app_proxy access scope in the app's scopes to configure an app proxy; the access-scopes reference lists write_app_proxy as granting 'App proxy configuration'.
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies
- **RISK-02** [confirmed, confidence low] COMMUNITY (not primary): Shopify staff 'KyleG-Shopify' cited a November 14, 2025 deadline for adding write_app_proxy; a developer reported in 2026 that a proxy still worked without the scope. Enforcement is unclear; include the scope anyway since the docs require it.
  Source: https://community.shopify.dev/t/app-proxy-access-scope-deadline/16834
- **SC-49** [confirmed, design-critical, confidence high] Shopify appends these query parameters to every proxied request: shop, logged_in_customer_id, path_prefix, timestamp, signature. They stay in the URL query string even for POST requests with a body.
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies/authenticate-app-proxies
- **SC-50** [confirmed, design-critical, confidence high] Parameter semantics: shop = the {shop}.myshopify.com domain (not the custom domain); logged_in_customer_id = customer ID or empty string when not logged in (parameter is still present); path_prefix = the prefix+subpath actually proxied (e.g. /apps/awesome_reviews); timestamp = Unix epoch seconds.
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies/authenticate-app-proxies
- **SC-51** [confirmed, design-critical, confidence high] Exact signature algorithm (official Ruby): parse the query string; remove `signature`; for every remaining parameter build "key=value" where repeated keys are joined with a comma (extra=1&extra=2 -> "extra=1,2"); sort the resulting strings lexicographically; concatenate with NO separator; HMAC-SHA256 with the app's shared secret as key; lowercase hex digest; constant-time compare to `signature`.
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies/authenticate-app-proxies
- **SC-52** [confirmed, design-critical, confidence high] The signed string uses URL-decoded ('unencoded') parameter values (the example parses path_prefix=%2Fapps%2Fawesome_reviews with Rack before signing), and empty values must be kept (e.g. "logged_in_customer_id="). The key is described as the application's 'shared secret'.
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies/authenticate-app-proxies
- **SC-53** [confirmed, design-critical, confidence high] The signature is hex-encoded HMAC-SHA256 (not base64 like webhook HMACs) and is carried in the `signature` query parameter (not `hmac`, not a header).
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies/authenticate-app-proxies
- **SC-54** [confirmed, design-critical, confidence medium] The app proxy page calls the key 'shared secret' and never names 'client secret'; the client-secrets page describes the client secret as the app's signing secret for OAuth and webhooks. That the app-proxy shared secret equals the Dev Dashboard Client secret is an inference from these pages, not an explicit statement; confirm with a live request.
  Source: https://shopify.dev/docs/apps/build/authentication-authorization/client-secrets
- **SC-55** [confirmed, design-critical, confidence medium] Documented example vector: secret 'hush', params extra=1&extra=2, logged_in_customer_id=1, path_prefix=/apps/awesome_reviews, timestamp=1317327555 -> signature 4c68c8624d737112c91818c11017d24d334b524cb5c2b8ba08daa056f7395ddb (anonymous variant: e072b6d7e6622d85912a5214b860d3100dc1e73d9bc29f43796ac8c9ff8093cb). The published query string contains a literal '{shop}.myshopify.com' placeholder, so recompute before using it as a unit-test fixture (I did not verify the digests).
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies/authenticate-app-proxies
- **SC-56** [confirmed, design-critical, confidence high] Shopify may add new query parameters at any time, so the verifier must sign over ALL received parameters except `signature`, never over a fixed allow-list. The client's own query parameters are also included in the signed set.
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies/authenticate-app-proxies
- **SC-57** [confirmed, design-critical, confidence high] A valid signature only proves the query string was produced by Shopify and not tampered with; the request body is not part of the signed data (signature is computed over query parameters only), and the app must itself authorize on logged_in_customer_id when returning customer data.
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies/authenticate-app-proxies
- **SC-58** [confirmed, design-critical, confidence medium] The HTTP method and the request body are forwarded to the proxy URL (docs mention form submissions and AJAX requests). A JSON body is not named explicitly; forwarding of Content-Type: application/json bodies is implied by 'request body' but not spelled out.
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies/authenticate-app-proxies
- **SC-59** [confirmed, confidence high] Not all HTTP methods are proxied: CONNECT and TRACE are unsupported (stated in the checkout UI-extension capabilities page about the App Proxy). GET and POST are shown/implied as supported; no complete list of supported methods is published.
  Source: https://shopify.dev/docs/apps/build/checkout/capabilities
- **SC-60** [confirmed, confidence high] Forwarding example: client GET /apps/awesome_reviews/extra/path/components?extra=1&extra=2 becomes GET /proxy/extra/path/components?extra=1&extra=2&shop=...&logged_in_customer_id=1&path_prefix=%2Fapps%2Fawesome_reviews&timestamp=...&signature=... on the proxy host; the sub-path and the client's own query params are preserved.
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies/authenticate-app-proxies
- **SC-61** [confirmed, confidence high] Shopify adds two headers to the forwarded request: X-Forwarded-Host (domain of the client's request, i.e. the storefront domain) and X-Forwarded-For (client IP).
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies/authenticate-app-proxies
- **SC-62** [confirmed, design-critical, confidence high] Cookies do not work through an app proxy in either direction: the Cookie request header is removed before forwarding and Set-Cookie is removed from the response. The middleware cannot read storefront cookies (e.g. the cart cookie) nor set its own session cookie.
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies/authenticate-app-proxies
- **SC-63** [confirmed, confidence high] Response headers stripped by the proxy (19): Accept-Patch, Accept-Ranges, Connection, Cookie, Date, Delta-Base, IM, P3P, Pragma, Preference-Applied, Proxy-Authenticate, Public-Key-Pins, Server, Service-Worker-Allowed, Set-Cookie, Trailer, Tk, Warning, X-Powered-By. Content-Type, Cache-Control and Location are not on the list.
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies
- **SC-64** [confirmed, confidence high] On the request side the docs name only Cookie as stripped and add that other (unnamed) headers are stripped too; whether custom request headers or Authorization survive is not documented, so pass everything the backend needs in the JSON body or query string.
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies/authenticate-app-proxies
- **SC-65** [confirmed, confidence high] Response handling: if the proxy response has Content-Type: application/liquid, Shopify renders the Liquid in the shop's theme context; any other content type (e.g. application/json, text/javascript) is passed back to the browser as-is.
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies
- **SC-66** [confirmed, design-critical, confidence medium] Redirects: the docs state that 30x responses from the proxy backend are 'followed'. Exact semantics (followed server-side by Shopify vs passed to the browser, cross-origin Location to another store's checkout) are not specified.
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies
- **RISK-03** [confirmed, design-critical, confidence medium] COMMUNITY (not primary; Shopify staff 'KyleG-Shopify', June 2026 thread): the proxy forwards with a trailing slash and a backend redirect issued through the proxy resolved against the storefront domain, producing a 404; also empty query params must be preserved for HMAC. Implication: never answer the proxy with a 3xx; return 200 JSON containing the checkoutUrl and let the theme script navigate.
  Source: https://community.shopify.dev/t/app-proxy-redirects-to-storefront-path-instead-of-proxying-302-404-dev-dashboard-app/35101
- **SC-67** [confirmed, confidence high] Password-protected stores: the only documented statement concerns checkout/customer-account UI extensions calling the App Proxy (not supported). Behaviour of ordinary storefront requests to an app proxy path on a password-protected store is not documented.
  Source: https://shopify.dev/docs/apps/build/checkout/capabilities
- **SC-68** [confirmed, design-critical, confidence high] App proxy timeouts, response size limits, rate limits and caching behaviour (whether Shopify/CDN caches proxied responses or honours Cache-Control) are not mentioned on the app proxy page or its authentication page: the words timeout, cache, CORS, POST, method, JavaScript and script do not appear on the main page.
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies
- **SC-69** [partially_correct, design-critical, confidence high] No timestamp freshness window or replay-protection requirement is documented for app proxy signatures; the page only defines the timestamp field. Any max-age check (e.g. reject if older than N seconds) is the middleware's own design choice.
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies/authenticate-app-proxies
  **CORRECTION:** True for the docs pages (no freshness rule is written). But Shopify's own library is not neutral on this: shopify-app-js hmac-validator checks the timestamp for app proxy requests with "HMAC_TIMESTAMP_PERMITTED_CLOCK_TOLERANCE_SEC = 90". So a 90-second window is Shopify's de facto reference, not purely a free design choice. (Source is Shopify's official GitHub library, not shopify.dev.) (https://raw.githubusercontent.com/Shopify/shopify-app-js/main/packages/apps/shopify-api/lib/utils/hmac-validator.ts)
- **SC-70** [confirmed, confidence medium] If the app is not installed on the shop that issues a proxied request, the official library exposes no admin/storefront context; i.e. proxy requests are tied to an installation of the app on that store.

## Design implications

- Organization is the gating prerequisite. Client credentials AND multi-store install of one Dev Dashboard app both require the app and every store to be in the same organization. For non-Plus stores this means the merchant must first group all vitrine and checkout stores into one organization (same store owner on every store, same billing currency, no INR-billed store). Stores that cannot be grouped need a separate app per organization (one client_id/client_secret per org) or custom distribution + authorization code grant.
- Create the app(s) from the merchant organization's Dev Dashboard (store admin > Settings > Apps > Develop apps > Build apps in Dev Dashboard), not from a Partner organization: community staff answers say Partner-org apps get shop_not_permitted on merchant production stores.
- Store credentials per app/organization rather than assuming one per store; several stores in one org can share one client_id/client_secret, while the token is per shop (endpoint is per {shop}.myshopify.com).
- Token manager: cache one Admin token per shop, treat expires_in (86399 s) as authoritative, renew about 60 s early by repeating the POST; there is no refresh token. On any 401 from the Admin API, re-mint once and retry. Because invalidation-on-reissue is undocumented, serialize token minting per shop (single-flight) so concurrent workers do not race.
- On every token response compare the returned `scope` string with the scopes the middleware needs and raise an operator alert if one is missing: scope changes need a new released version plus approval on each store, and the docs disagree on whether that approval is automatic for own-org apps.
- Handle `shop_not_permitted` as a permanent configuration error (store not in the app's organization), not as a retryable failure; surface it in onboarding with the instruction to group the store or use a different app.
- Pin the Admin API and webhooks API version explicitly to 2026-10 in configuration; do not copy the 2025-01 version string from Shopify's client-credentials sample.
- App proxy verification must: take the raw query string, URL-decode values, drop `signature`, keep empty values (logged_in_customer_id=), join repeated keys with ',', sort 'k=v' strings, concatenate without separator, HMAC-SHA256 with the client secret, hex, constant-time compare. Sign over ALL parameters received (Shopify may add new ones). Frameworks that drop empty params or re-encode the query will break verification, so work from the raw query string.
- The signature does not cover the POST body. Treat cart lines in the body as untrusted input (already the plan: variant IDs + quantities only, prices from the checkout store). Use the signed `shop` parameter, never a body field, to decide which vitrine store the request belongs to.
- Add your own replay window on `timestamp` (not specified by Shopify) and verify against every unrevoked client secret so that secret rotation does not break the checkout button; re-mint all tokens before revoking the old secret.
- Do not rely on cookies or custom headers through the proxy (Cookie/Set-Cookie are stripped, other request headers may be). The theme script must read /cart.js in the browser and send lines in the body; any correlation id must travel in the body or query string.
- Do not respond to the proxied POST with a 3xx to the checkout store: redirect semantics through the proxy are under-documented and a staff community answer reports redirects resolving against the storefront domain. Return 200 application/json with { checkoutUrl } and let the theme script do window.location.assign; make the backend route tolerate a trailing slash without redirecting.
- Because timeout, caching and password-page behaviour of app proxies are undocumented, keep the proxy handler fast (variant mapping from a local table, one cartCreate call), send Cache-Control: no-store on the POST response, implement a client-side timeout with the cart-permalink fallback, and test explicitly on a password-protected store before launch.
- Include write_app_proxy in the app's scopes and configure [app_proxy] (prefix one of a/apps/community/tools; subpath <= 30 chars, not admin/services/password/login). Only one proxy route per app. Changing prefix/subpath later only affects new installs and merchants can rename the path per store, so make the proxy path a per-store setting in the theme script (or read it from a theme setting) rather than hard-coding it.
- Script delivery options, in order of documented support: (1) merchant pastes/maintains the small script in each vitrine theme manually (no API needed, own stores); (2) theme app extension with an app embed block (requires linking the app to Shopify CLI and a one-time manual activation per theme; assets served from Shopify CDN; keep JS near the 10 KB suggested size); (3) serving the JS from the app proxy with Content-Type text/javascript (works per community/staff answer, no official statement, caching unknown); (4) themeFilesUpsert (write_themes; exemption requirement for non-public apps is ambiguous, must be tested). ScriptTag API is closed for new tags since 2026-10-01 and stops running on 2027-03-01, so it must not be used.
- A single app can serve both roles (vitrine with app proxy, checkout with Admin/Storefront access) only if all stores share the organization; otherwise plan one app per organization and keep the proxy secret lookup keyed by the signed `shop` value.

## Additional facts found by the verifier

- Shopify's official library (not shopify.dev docs) settles two points the docs leave open. It signs app proxy checks with the app secret, in hex: "createSHA256HMAC(config.apiSecretKey, queryString, HashFormat.Hex)", which supports SC-54 (shared secret = client secret). It also rejects stale requests: "HMAC_TIMESTAMP_PERMITTED_CLOCK_TOLERANCE_SEC = 90". Use 90 seconds as the replay window rather than inventing one.
  Source: https://raw.githubusercontent.com/Shopify/shopify-app-js/main/packages/apps/shopify-api/lib/utils/hmac-validator.ts
- The same official library refuses duplicated security parameters: "APP_PROXY_SINGLE_VALUE_PARAMS = new Set(['hmac', 'shop', 'signature', 'timestamp'])". The middleware verifier should likewise reject a request where shop, timestamp or signature appears more than once, instead of comma-joining them, otherwise a client-appended second shop value could confuse store resolution.
  Source: https://raw.githubusercontent.com/Shopify/shopify-app-js/main/packages/apps/shopify-api/lib/utils/hmac-validator.ts
- Sort-order subtlety between Shopify's two reference implementations: the Ruby doc sample sorts the complete "key=value" strings, while the JS library sorts by key only (".sort(([val1], [val2]) => val1.localeCompare(val2))"). They agree for Shopify's own parameters but can differ for unusual client-supplied keys (for example a and a1, or mixed case). Design consequence: have the theme script send NO query parameters of its own on the proxy call (everything in the POST body) and implement the Ruby rule.
  Source: https://shopify.dev/docs/apps/build/online-store/app-proxies/authenticate-app-proxies
- A primary source (Help Center), not only community posts, states that merchant-created Dev Dashboard custom apps use this grant: "your developer needs to use the client credentials grant flow to generate an access token". This upgrades RISK-01's implication (create the app from the store admin's Dev Dashboard) from community-level to documented.
  Source: https://help.shopify.com/en/manual/apps/install-setup-apps
- Cross-topic but changes token design: the Storefront API works without any token for cart operations. Tokenless access covers "Products and Collections, Selling Plans, Search, Pages, Blogs, and Articles, Cart (read/write)" with "a query complexity limit of 1,000". cartCreate on the checkout store may therefore need no Storefront token at all; tokens are required only for product tags, metaobjects/metafields, menus and customers. Private tokens, if used, also need the Shopify-Storefront-Buyer-IP header.
  Source: https://shopify.dev/docs/api/storefront
- Fallback for stores that cannot be grouped into the organization is less painful than implied: non-expiring offline tokens are still available to custom apps through the authorization code grant. The restriction on them targets public apps and "This doesn't apply to custom apps or apps created by merchants." (expiring=0 is the default; expiring offline tokens last 1 hour with a 90-day refresh token).
  Source: https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens
- Token invalidation events are documented: "A merchant uninstalling your app, or you revoking the client secret, ends all of a token's access." The token cache must be dropped on app/uninstalled and after secret revocation; a 401 mid-lifetime is expected in those cases, not only at the 24-hour expiry.
  Source: https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens
- Custom-distribution install links (the route for stores outside the organization) are single-store and short-lived: "Custom app installation links are specific to your store, and can't be used to install the app on another store." and "custom install links expire after seven days". Onboarding for an out-of-organization store needs one fresh link per store.
  Source: https://help.shopify.com/en/manual/apps/install-setup-apps
- Fall-forward can be detected at runtime: "API responses include the `X-Shopify-API-Version` header reflecting the version used to fulfill the request." The middleware should log an alert when this header differs from the pinned 2026-10. Note 2026-10 is accessible only until October 16, 2027 15:00 UTC, so a yearly version bump is mandatory.
  Source: https://shopify.dev/docs/api/usage/versioning
- A webhook exists for scope approval: "The `app/scopes_update` webhook fires when the merchant approves the changes." Subscribing to it lets the middleware re-mint the token and re-check the scope readback immediately instead of waiting for the next 24-hour renewal.
  Source: https://shopify.dev/docs/apps/build/authentication-authorization/app-installation/manage-access-scopes
- Grouping stores resets organization-level permissions: "users keep their store permissions, but their organization permissions are removed." Dev Dashboard access is an organization-level permission (the Help Center says collaborators lack it for that reason), so staff may lose Dev Dashboard access after grouping and need the App developer role reassigned. What happens to apps already created in a store's previous standalone organization is not documented; group the stores BEFORE creating the app.
  Source: https://help.shopify.com/en/manual/your-account/manage-orgs-and-stores/manage-orgs/group-store
- UI label mismatch to expect during setup: the Dev Dashboard tutorial says "From your app in the Dev Dashboard, select App settings. Copy your Client ID and Client secret", while the credentials pages say Apps > app > Settings > Credentials. Help Center names the version form sections URLs, Webhooks API Version and Access. Write setup instructions tolerant of both labels.
  Source: https://shopify.dev/docs/apps/build/dev-dashboard/create-apps-using-dev-dashboard
- COMMUNITY (risk only, not primary): shop_not_permitted is reported as HTTP 400 Bad Request, and a second undocumented token-endpoint error exists, application_cannot_be_found, which staff (Alan_G, Apr 10, 2026) say "usually pops up when the Client ID being passed doesn't match what we have on file for the app". Treat both as permanent configuration errors, not retryable.
  Source: https://community.shopify.dev/t/dev-dashboard-custom-app-returns-application-cannot-be-found-on-admin-oauth-access-token-is-client-credentials-even-supported/33138
- COMMUNITY (risk only, no staff reply): when the proxy backend answers a POST with a 500, the proxy does not pass the error body to the browser; the client instead received the shop's HTML page, observed as a 302. The theme script must treat anything that is not a 200 with parseable JSON containing checkoutUrl as a failure and go to the cart-permalink fallback; the backend should never rely on error bodies reaching the browser.
  Source: https://community.shopify.dev/t/shopify-app-proxy-not-forwarding-post-requests-to-backend/23917
- COMMUNITY (risk only, no staff reply): on a password-protected storefront, app proxy requests are redirected to the password page once the storefront password session lapses; a developer reported "it suddenly takes me to the page to enter password". Expect HTML/redirect instead of JSON on password-protected vitrine stores during testing; another reason for the non-JSON fallback path.
  Source: https://community.shopify.dev/t/dev-stores-password-session-expires-very-quickly/20765
- COMMUNITY (risk only; developer test dated Sep 2, 2026, no staff reply): JSON POST bodies were forwarded correctly through an app proxy, and a proxy added via [app_proxy] went live on an already-installed store about 15 seconds after release with no reinstall, with or without write_app_proxy granted. This is the only evidence found for JSON body forwarding; official docs still only say method and body are forwarded.
  Source: https://community.shopify.dev/t/tested-app-proxy-works-with-app-proxy-config-alone-without-write-app-proxy-is-the-scope-enforced-anywhere/37388
- COMMUNITY (risk only, no staff reply): Cache-Control headers set by the backend on app proxy Liquid responses reportedly had no effect. Do not design around CDN caching of proxied responses (relevant if the theme script itself were served through the proxy); host the script as a theme asset or app embed instead.
  Source: https://community.shopify.dev/t/caching-app-proxy-liquid-response/29426
