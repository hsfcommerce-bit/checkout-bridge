# Storefront API: server-side auth and cartCreate (researched 2026-10-05 against shopify.dev / help.shopify.com; quotes were extracted through the WebFetch summarising reader, so field lists should be re-confirmed by schema introspection before coding)

Researched on 2026-10-05 from Shopify primary documentation. Each claim was re-checked by an independent verifier;
the verdict is shown in brackets. "CORRECTION" lines override the claim they follow. Items marked community/RISK are not official.

## Claims

- **SF-01** [confirmed, confidence high] The latest stable API version is 2026-10 (released 2026-10-01, accessible until 2027-10-16 15:00 UTC); 2027-01 is the release candidate. The Storefront API reference, cartCreate, CartInput and CartLineInput pages all render as version 2026-10.
  Source: https://shopify.dev/docs/api/usage/versioning
- **SF-02** [confirmed, confidence high] Endpoint format is POST https://{store_name}.myshopify.com/api/2026-10/graphql.json. There is a single GraphQL endpoint and it only accepts POST.
  Source: https://shopify.dev/docs/api/storefront/latest
- **SF-03** [confirmed, confidence high] Versions are released quarterly and supported at least 12 months; calling a version that is no longer accessible does not fail, Shopify silently answers with the oldest accessible stable version (so behaviour can change without an error).
  Source: https://shopify.dev/docs/api/usage/versioning
- **SF-04** [confirmed, confidence high] cartCreate takes one argument `input: CartInput` and returns CartCreatePayload { cart: Cart, userErrors: [CartUserError!]!, warnings: [CartWarning!]! }. The cart returned already contains checkoutUrl.
  Source: https://shopify.dev/docs/api/storefront/latest/mutations/cartCreate
- **SF-05** [confirmed, confidence high] CartInput (2026-10) fields: attributes [AttributeInput!], buyerIdentity CartBuyerIdentityInput, delivery CartDeliveryInput, discountCodes [String!], giftCardCodes [String!], lines [CartLineInput!], metafields [CartInputMetafieldInput!], note String, sourceName String. All are optional.
  Source: https://shopify.dev/docs/api/storefront/latest/input-objects/CartInput
- **SF-06** [confirmed, design-critical, confidence high] Documented per-request array limits on CartInput: lines, attributes, discountCodes, giftCardCodes and metafields each accept at most 250 values. CartLineInput.attributes is also capped at 250 values. The 250 cap is a platform-wide rule for array inputs.
  Source: https://shopify.dev/docs/api/usage/limits
- **SF-07** [confirmed, design-critical, confidence high] A cart can hold at most 500 line items in total (separate from the 250-per-request input cap). No maximum per-line quantity is stated on the pages read.
  Source: https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/cart
- **SF-08** [confirmed, design-critical, confidence high] CartLineInput (2026-10) fields: merchandiseId ID! (required), quantity Int (default 1), attributes [AttributeInput!] (max 250), sellingPlanId ID, parent CartLineParentInput. There is no price field: price cannot be supplied by the caller.
  Source: https://shopify.dev/docs/api/storefront/latest/input-objects/CartLineInput
- **SF-09** [confirmed, confidence medium] AttributeInput has exactly two fields, key String! and value String!. No key/value length limit is documented on the reference page.
  Source: https://shopify.dev/docs/api/storefront/latest/input-objects/AttributeInput
- **SF-10** [confirmed, confidence high] CartBuyerIdentityInput fields: companyLocationId ID, countryCode CountryCode, customerAccessToken String, email String, phone String, preferences CartPreferencesInput, and deliveryAddressPreferences [DeliveryAddressInput!] (deprecated).
  Source: https://shopify.dev/docs/api/storefront/latest/input-objects/CartBuyerIdentityInput
- **SF-11** [confirmed, confidence medium] CartInput.sourceName sets order attribution and must match a channel source name owned by the API client behind the token. Per the 2026-06-30 changelog (API 2026-07), an unmatched sourceName falls back to app-only attribution rather than failing.
  Source: https://shopify.dev/docs/api/storefront/latest/input-objects/CartInput
- **SF-12** [confirmed, confidence high] CartUserError has fields code: CartErrorCode, field: [String!] (path to the offending input field) and message: String!.
  Source: https://shopify.dev/docs/api/storefront/latest/objects/CartUserError
- **SF-13** [partially_correct, design-critical, confidence high] CartErrorCode values relevant to invalid merchandise/quantity: INVALID, INVALID_MERCHANDISE_LINE, MERCHANDISE_NOT_APPLICABLE, MAXIMUM_EXCEEDED, MINIMUM_NOT_MET, INVALID_INCREMENT, LESS_THAN, VARIANT_REQUIRES_SELLING_PLAN, SELLING_PLAN_NOT_APPLICABLE, CART_TOO_LARGE, NOTE_TOO_LONG, INVALID_METAFIELDS, VALIDATION_CUSTOM, MERCHANDISE_LINE_TRANSFORMERS_RUN_ERROR, SERVICE_UNAVAILABLE. There is no dedicated 'variant not found' or 'not published' code.
  Source: https://shopify.dev/docs/api/storefront/latest/enums/CartErrorCode
  **CORRECTION:** All 15 listed codes exist and there is no 'variant not found' / 'not published' code. But INVALID_MERCHANDISE_LINE is documented as "Merchandise line was not found in cart." - it concerns a cart LINE id (update/remove mutations), not a bad merchandiseId on cartCreate. Which code (if any) a non-existent, wrong-shop or unpublished merchandiseId returns is not documented. (https://shopify.dev/docs/api/storefront/latest/enums/CartErrorCode)
- **SF-14** [confirmed, design-critical, confidence high] CartWarningCode stock/availability values: MERCHANDISE_NOT_ENOUGH_STOCK, MERCHANDISE_OUT_OF_STOCK, PRODUCT_UNAVAILABLE_IN_BUYER_LOCATION. Others: twelve DISCOUNT_* codes (e.g. DISCOUNT_NOT_FOUND, DISCOUNT_CODE_NOT_HONOURED), DUPLICATE_DELIVERY_ADDRESS, MERCHANDISE_SELLING_PLAN_NOT_APPLICABLE_ON_COMPANY_LOCATION, PAYMENTS_GIFT_CARDS_UNAVAILABLE.
  Source: https://shopify.dev/docs/api/storefront/latest/enums/CartWarningCode
- **SF-15** [confirmed, design-critical, confidence high] Stock problems arrive in `warnings`, not `userErrors`: a warning means the mutation succeeded and Shopify changed the cart automatically. CartWarning fields are code: CartWarningCode!, message: String!, target: ID! (the affected cart line ID). So an empty userErrors array does not mean the cart matches what was requested.
  Source: https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/cart/cart-warnings
- **SF-16** [confirmed, design-critical, confidence medium] In the cart-warnings guide example an out-of-stock line stays in the cart with quantity 0 and a MERCHANDISE_OUT_OF_STOCK warning targeting that line; what MERCHANDISE_NOT_ENOUGH_STOCK does to the quantity is not spelled out. (Example detail reported by the fetch reader, not quoted in full.)
  Source: https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/cart/cart-warnings
- **SF-17** [unverifiable, design-critical, confidence low] RISK (community forum post, March 2025, not official docs): cartCreate with a variant that is not published to the calling app's sales channel returned a cart with no lines and no userErrors. Shopify staff acknowledged it without a documented fix.
  Source: https://community.shopify.dev/t/when-we-create-cart-using-storefront-api-and-if-the-product-is-not-published-on-the-sales-channel-it-did-not-show-any-error-message/9939
  **CORRECTION:** Community only. - **SF-18** [confirmed, design-critical, confidence high] Cart.cost (CartCost!) is explicitly an estimate and is priced from the cart's buyerIdentity. Fields: totalAmount MoneyV2!, totalAmountEstimated Boolean!, subtotalAmount MoneyV2!, subtotalAmountEstimated Boolean!, checkoutChargeAmount MoneyV2!; totalTaxAmount/totalDutyAmount (and their *Estimated flags) are deprecated.
  Source: https://shopify.dev/docs/api/storefront/latest/objects/Cart
- **SF-19** [confirmed, design-critical, confidence high] Per-line confirmation is available on CartLine.cost (CartLineCost): amountPerQuantity MoneyV2!, compareAtAmountPerQuantity MoneyV2, subtotalAmount MoneyV2!, totalAmount MoneyV2!. CartLine also exposes id, quantity Int!, merchandise, attributes, discountAllocations, sellingPlanAllocation.
  Source: https://shopify.dev/docs/api/storefront/latest/objects/CartLineCost
- **SF-20** [confirmed, design-critical, confidence medium] On the line's merchandise (ProductVariant) the server can read price MoneyV2!, compareAtPrice, availableForSale Boolean!, currentlyNotInStock Boolean!, sku, barcode, selectedOptions. quantityAvailable Int is annotated as requiring token access (not available tokenless) and is gated by the unauthenticated_read_product_inventory scope.
  Source: https://shopify.dev/docs/api/usage/access-scopes
- **SF-21** [confirmed, confidence high] checkoutUrl (URL!) should be fetched at the moment of redirect and not cached; it can go stale and be re-requested from the cart.
  Source: https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/cart/manage
- **SF-22** [confirmed, confidence low] The docs do not state a rule for which domain checkoutUrl uses. The only evidence is the guide's example response, which shows the myshopify.com host and a /cart/c/<token> path. Hydrogen docs tell merchants to point a subdomain at the Online Store target as Primary for checkout, which implies (not states) checkout is served on the Online Store primary domain.
  Source: https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/cart/manage
- **SF-23** [confirmed, design-critical, confidence high] The cart ID is `<token>?key=<secret>`; the key must be kept server-side. Queries without the key strip buyer private details and mutations without the key fail. Token format/length may change at any time, so store it as an opaque string.
  Source: https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/cart/manage
- **SF-24** [confirmed, design-critical, confidence high] Cart lifetime: unused/abandoned carts expire within 30 days of creation. What the cart query returns for an expired cart is not described on the pages read.
  Source: https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/cart
- **SF-25** [partially_correct, confidence medium] The only query parameter documented as appendable to a Storefront cart checkoutUrl is sso=silent (previously logged_in=true) for silent customer SSO. Appending discount, locale, UTM or other parameters to checkoutUrl is not documented (those are documented for cart permalinks only).
  Source: https://shopify.dev/changelog/headless-checkout-sso-is-now-documented-with-ssosilent
  **CORRECTION:** sso=silent / logged_in=true is confirmed (changelog 8 June 2026). But 'not documented' is too strong: the agents doc shows a checkout URL of the same shape (/cart/c/abc123?key=xyz789&utm_source=...) and says "You can append query parameters to prefill buyer information, apply discounts, add custom tracking data", linking the cart-permalink 'supported checkout parameters'. That text is about the Catalog checkout_url, not explicitly Storefront cart.checkoutUrl, so it still needs a test. Language is set via @inContext(language:) on cartCreate, not a URL parameter. (https://shopify.dev/docs/agents/carts-and-checkout.md)
- **SF-26** [confirmed, confidence high] Cart attributes carry over to the order. The Attribute type is shared by carts, cart lines, orders and order line items; the page does not separately state that line-level attributes become order line-item attributes, though the shared type implies it.
  Source: https://shopify.dev/docs/api/storefront/latest/objects/Attribute
- **SF-27** [unverifiable, confidence low] RISK (community forum, Shopify staff reply, not official docs): attributes only reach the order if they are set before the buyer enters checkout; attributes updated after checkout has started were not pulled in without a reload.
  Source: https://community.shopify.dev/t/cart-attributes-rarely-carry-over-to-customattributes-on-order-object/23367
  **CORRECTION:** Community only. Thread exists (Oct-Nov 2025); staff quote verified: "As long as they are set and the checkout URL is using the proper key parameters." For buyers already in checkout staff said "You would need to use checkout extensions for that" or orderUpdate afterwards. Not in primary docs. (https://community.shopify.dev/t/cart-attributes-rarely-carry-over-to-customattributes-on-order-object/23367)
- **SF-28** [confirmed, confidence medium] For the cart-permalink fallback, note and attributes[...] query parameters are documented as landing on the order; permalinks do not support selling plans and cannot bypass a storefront password; an access_token parameter attributes the order to a sales channel.
  Source: https://shopify.dev/docs/apps/build/checkout/create-cart-permalinks
- **SF-29** [confirmed, design-critical, confidence high] Tokenless access (no auth header at all) is documented to cover Products and Collections, Selling Plans, Search, Pages/Blogs/Articles, and Cart read/write, so cartCreate is documented as working without any token.
  Source: https://shopify.dev/docs/api/storefront/latest
- **SF-30** [confirmed, design-critical, confidence high] Tokenless requests are capped at query complexity 1,000 (cost-per-field calculation); exceeding it returns an error. Product tags, metaobjects, metafields, menus and customers require a token.
  Source: https://shopify.dev/docs/api/storefront/latest
- **SF-31** [confirmed, design-critical, confidence high] Public access token: sent in X-Shopify-Storefront-Access-Token, created with the Admin GraphQL mutation storefrontAccessTokenCreate, intended for browsers/mobile apps. Its capacity is keyed to buyer IP, so calling with it from one server IP concentrates all traffic on one IP.
  Source: https://shopify.dev/docs/api/storefront/latest
- **SF-32** [confirmed, design-critical, confidence high] storefrontAccessTokenCreate(input: StorefrontAccessTokenInput! { title }) returns { shop, storefrontAccessToken { accessToken, accessScopes, title, id, createdAt, updatedAt }, userErrors }. Limit: 100 active storefront access tokens per app per shop.
  Source: https://shopify.dev/docs/api/admin-graphql/latest/objects/StorefrontAccessToken
- **SF-33** [confirmed, design-critical, confidence high] A storefront access token inherits every unauthenticated_* scope the creating app has been granted; creation fails if the app has none. So the unauthenticated scopes must be on the app before the token is minted.
  Source: https://shopify.dev/docs/api/admin-rest/latest/resources/storefrontaccesstoken
- **SF-34** [confirmed, design-critical, confidence high] Private access token: sent in Shopify-Storefront-Private-Token, for server contexts, must never reach the client. Three documented ways to get one: Headless channel, a delegate access token for a custom app, or unauthenticated scopes on an existing access token (the third option is not explained further).
  Source: https://shopify.dev/docs/api/storefront/latest
- **SF-35** [confirmed, design-critical, confidence high] Delegate tokens are created with Admin GraphQL delegateAccessTokenCreate (input delegateAccessScope: required scope list, expiresIn: optional seconds) and used on the Storefront API as a private token. Only the app's own access token can create them, and only for scopes the app already holds.
  Source: https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens/use-delegate-tokens
- **SF-36** [confirmed, design-critical, confidence high] Delegate tokens cannot outlive their parent token: with expiresIn omitted they expire with the parent, a longer expiresIn is rejected (error code EXPIRES_AFTER_PARENT), and refreshing the parent does not extend existing delegates.
  Source: https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens/use-delegate-tokens
- **SF-37** [confirmed, design-critical, confidence high] Client-credentials Admin tokens always expire after 24 hours (expires_in 86399) and only work when app and store are in the same Shopify organization. Combined with SF-36, a delegate private Storefront token minted from such a token lives at most about 24 hours and must be re-minted after every parent refresh.
  Source: https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens/client-credentials-grant
- **SF-38** [partially_correct, design-critical, confidence high] Headless channel: installing it and clicking Create storefront generates a public and a private token without any custom app; max 100 active storefronts/tokens per shop; permissions are edited per storefront in admin; rotating generates a new private token while the old one keeps working until deleted. No expiry is documented.
  Source: https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/manage-headless-channels

- **SF-39** [confirmed, design-critical, confidence high] Scopes: Cart (cartCreate and cart reads) = unauthenticated_write_checkouts / unauthenticated_read_checkouts; Product, ProductVariant, Collection = unauthenticated_read_product_listings; quantityAvailable = unauthenticated_read_product_inventory; selling plans = unauthenticated_read_selling_plans; Product.tags = unauthenticated_read_product_tags.

## Not documented by Shopify

- Q2: maximum quantity per cart line - no numeric limit on CartLineInput, Cart or the cart overview page (only per-variant quantity rules surfaced through MAXIMUM_EXCEEDED / MINIMUM_NOT_MET / INVALID_INCREMENT).
- Q2: maximum length of attribute keys/values and of the cart note (NOTE_TOO_LONG exists but no number is given).
- Q2: which userError code/message cartCreate returns for a non-existent, wrong-shop or unpublished merchandiseId. No official example; a community report says an unpublished variant yields an empty cart with no error.
- Q2: exact behaviour of MERCHANDISE_NOT_ENOUGH_STOCK (whether quantity is clamped to available stock) and whether an out-of-stock line blocks checkout.
- Q2: scope annotation on the cartCreate page itself - none shown; the Cart scope mapping comes from the access-scopes page.
- Q3: which domain checkoutUrl uses (myshopify.com vs the Online Store primary domain) - no rule stated; only an example URL on myshopify.com.
- Q3: how long a checkoutUrl stays valid ('stale' is not quantified) and what the cart query returns for an expired or completed cart.
- Q3: whether arbitrary query parameters (discount, locale, UTM, ref) may be appended to a Storefront cart checkoutUrl - only sso=silent / logged_in=true is documented.
- Q3: whether the cart `note` and line-level attributes land on the order (order note / line item customAttributes / REST note_attributes and properties) - only cart-level attributes are explicitly said to carry over; the mapping to REST note_attributes is not stated in Storefront docs.
- Q4: whether public storefront access tokens (storefrontAccessTokenCreate) or Headless channel tokens ever expire - no expiry statement on any page read.
- Q4: whether storefrontAccessTokenCreate and delegateAccessTokenCreate accept an Admin token obtained through the client credentials grant from a Dev Dashboard app, and whether a storefront access token survives expiry of the 24-hour token that created it.
- Q4: what 'Request unauthenticated access scopes on an existing access token' means in practice - i.e. whether an Admin access token holding unauthenticated_* scopes can be sent directly in Shopify-Storefront-Private-Token.
- Q4: how unauthenticated_* scopes are added to a Dev Dashboard app (official docs read do not say required vs optional; only a community thread does).
- Q4: Admin API scope (if any) required to call storefrontAccessTokenCreate, beyond the app holding unauthenticated scopes.
- Q4/Q5: whether tokenless requests made from a server should or can send Shopify-Storefront-Buyer-IP, and how tokenless server-side traffic from a single IP is treated by bot protection.
- Q5: numeric values for the checkout-creation throttle and bot limits; any Retry-After style header for Storefront API throttling.
- Q6: whether cartCreate's buyerIdentity.countryCode for a country not in any market falls back to the primary market/store currency (the fallback sentence is written for queries).
- Q7: which products a non-sales-channel app (e.g. a Dev Dashboard app with only unauthenticated scopes and no channel) can see or add to cart.
- Q7: which publication tokenless access uses (Online Store or otherwise) - no statement found.
- Q7: whether a Dev Dashboard app gets a publication/channel automatically, and how a merchant publishes products to it in admin.

## Design implications

- Pin the checkout-store endpoint to https://{shop}.myshopify.com/api/2026-10/graphql.json (POST only). 2026-10 is accessible until 2027-10-16; after that Shopify silently falls forward, so schedule a version bump rather than waiting for errors.
- Send only merchandiseId + quantity (+ attributes) per line. CartLineInput has no price field, so prices necessarily come from the checkout store's catalog - this matches the 'never send prices' rule by construction.
- Enforce limits before calling: max 250 lines per cartCreate (platform array cap), 500 lines per cart, 250 attributes per cart and per line. Carts above 250 lines need cartCreate plus cartLinesAdd, or should be rejected.
- Never treat empty userErrors as success. After cartCreate, compare cart.lines (merchandise.id + quantity) and totalQuantity against what was requested, and read `warnings` (MERCHANDISE_OUT_OF_STOCK, MERCHANDISE_NOT_ENOUGH_STOCK, PRODUCT_UNAVAILABLE_IN_BUYER_LOCATION). A community report says unpublished variants are dropped silently, so a line-count mismatch must be handled as a mapping/publication failure.
- For charge confirmation and logging, select cost { totalAmount subtotalAmount checkoutChargeAmount totalAmountEstimated } and lines { quantity cost { amountPerQuantity totalAmount } merchandise { ... on ProductVariant { id sku price availableForSale } } }. All of it is an estimate; checkout remains authoritative.
- Auth choice is the main open design decision. Documented facts: tokenless covers cartCreate with no credentials (complexity cap 1,000, no quantityAvailable/metafields); a public token's capacity is keyed to buyer IP so it is a poor fit for a single server IP; private tokens are the documented server-side option.
- The current plan (client_id/client_secret + client credentials) gives 24-hour Admin tokens, and delegate private tokens inherit that expiry and are not extended by a refresh. If delegate tokens are used, build a per-store job that re-mints the delegate token after every Admin token refresh and swaps it atomically. A Headless channel private token avoids this (no documented expiry, manual rotation) but is a manual per-store setup step outside the Dev Dashboard app.
- Whether storefrontAccessTokenCreate / delegateAccessTokenCreate work with client-credentials tokens from a Dev Dashboard app is not documented; test this on a real store before committing to the design, and keep the tokenless and Headless-token paths as alternatives.
- Declare unauthenticated_write_checkouts, unauthenticated_read_checkouts and unauthenticated_read_product_listings as required (not optional) scopes on the app version for checkout stores; add unauthenticated_read_product_inventory only if quantityAvailable is needed and unauthenticated_read_selling_plans only if sellingPlanId is used. A storefront access token inherits scopes at creation, so mint tokens after scopes are granted.
- Capture the buyer's real IP on the vitrine request and forward it as Shopify-Storefront-Buyer-IP (case-sensitive) on every private-token call. Without it Shopify cannot tell buyers apart, and all traffic looks like one high-volume client; this is the documented cause to check on HTTP 430.
- Error handling must cover: HTTP 430 (security rejection), HTTP 200 with errors[].extensions.code THROTTLED (checkout-creation throttle) or ACCESS_DENIED, and 402/403/423 shop states. On any of these, fall back to the cart permalink path rather than retrying in a tight loop.
- Set pricing context explicitly: pass buyerIdentity.countryCode in cartCreate when the buyer's country is known (it overrides any @inContext country and is persisted to checkout); otherwise the primary market applies. Countries not enabled fall back to store currency, so the vitrine's displayed currency can differ from the checkout's.
- Product visibility is a hard dependency: every mapped variant on the checkout store must be published to whatever channel/publication the token resolves to (Headless channel for Headless tokens; the app's channel for app tokens; from 2026-10 the first channel owned by the API client unless @inContext(channelId:) is given). The catalog sync should record publication status and exclude or flag unpublished variants in the mapping table. Visibility for tokenless and for non-channel apps is undocumented and must be verified empirically.
- Put vitrine-origin metadata (source store, vitrine cart token, mapping version) in CartInput.attributes at creation time, before redirect - cart attributes are documented to carry to the order, and a staff forum reply indicates attributes changed after checkout starts may not. Do not rely on cart `note` or line attributes reaching the order without testing.
- Redirect to cart.checkoutUrl immediately from the cartCreate response; do not store or reuse it, and do not append custom query parameters (only sso=silent is documented). Do not assume its host; treat it as opaque. Keep the cart ID (it contains ?key=<secret>) server-side only.
- The cart-permalink fallback carries note/attributes to the order but does not support selling plans and cannot pass a password-protected storefront, so it is not equivalent to the cartCreate path for subscription items or locked stores.

## Additional facts found by the verifier

- Delegate tokens cannot be minted from a refreshable parent. DelegateAccessTokenCreateUserErrorCode includes REFRESH_TOKEN: "The parent access token can't have a refresh token." and DELEGATE_ACCESS_TOKEN: "The parent access token can't be a delegate token." The client-credentials response documents only access_token, scope and expires_in (no refresh token), so that grant looks compatible, but if the app ever switches to expiring offline tokens with refresh tokens the delegate (private token) path breaks. Must be tested on a real store.
  Source: https://shopify.dev/docs/api/admin-graphql/latest/enums/DelegateAccessTokenCreateUserErrorCode
- The checkout store has a per-variant add-to-cart limit that is on by default: "The maximum quantity per item setting is active by default." and "the default recommended limit for your store is set to 50" (stores with under 250 sales). The same page says the cart "automatically reduces the quantity to match your available inventory." So a requested quantity can come back lower; the page does not say how this surfaces in the Storefront API (warning vs userError). Setting is at Settings > Checkout > Advanced preferences > Add-to-cart limit; it does not apply to variants with inventory tracking off or 'continue selling when out of stock'.
  Source: https://help.shopify.com/en/manual/checkout-settings/add-to-cart-limit
- Completed carts are deleted, and cart creation itself is unbounded: "Shopify automatically deletes the cart when the customer completes their checkout." and "A shop or customer can create an unlimited number of carts." The middleware should not expect to re-read a cart after the order is placed; reconcile via order webhooks plus cart attributes instead.
  Source: https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/cart
- Checkout language is set at cart creation, not on the URL: "The `@inContext` directive can also be used with the `cartCreate` mutation to set the cart locale." The example cart "will load in Spanish when you redirect the customer to its `checkoutUrl`." Pass the vitrine's locale as @inContext(language:) on cartCreate.
  Source: https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/markets/multiple-languages
- RISK (community forum, Oct 2025, relaying Shopify partner support, not official docs): when the store's Online Store is password-protected, every checkoutUrl from cartCreate landed on the password page. Suggested workarounds were adding the query parameter "channel=headless-storefronts" to the checkoutUrl or removing the password. Together with the documented "Cart permalinks cannot bypass storefront passwords", this means a checkout store cannot simply be hidden behind the storefront password; test before relying on either path.
  Source: https://community.shopify.dev/t/every-checkouturl-ends-up-with-password-page-site-under-construction/24378
- RISK/evidence (community forum, Shopify staff, Apr-May 2026, not official docs): the Storefront API token section was removed from Dev Dashboard custom app settings and staff called it expected, telling developers to "use the `storefrontAccessTokenCreate` mutation on the Admin API to retrieve Storefront API tokens" after getting an Admin token with the client credentials grant; the Headless app was offered as the alternative. This is the only statement found that client-credentials tokens are meant to work with storefrontAccessTokenCreate.
  Source: https://community.shopify.dev/t/enable-storefront-api-no-more-available-for-custom-apps/33764
- Scope changes on a Dev Dashboard app need a released version AND approval on each store: "If a scope you need is missing, release a new version with it and approve the change on the store." The token response's `scope` field is "A readback of what you selected on your app's version in the Dev Dashboard", so the middleware can check that the unauthenticated_* scopes are actually granted before trying to mint a Storefront token.
  Source: https://shopify.dev/docs/apps/build/dev-dashboard/get-api-access-tokens
- The cart-warnings example is a cartLinesAdd call where a previously added line went out of stock (not a cartCreate with an out-of-stock variant). The doc says "Clients can choose to address an automatic change, but action isn't required" and that clients can use the warning target to call cartLinesRemove. The middleware should treat any returned line with quantity 0 or a warning target as a mismatch and decide (remove line, or abort the redirect) rather than assume Shopify drops it.
  Source: https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/cart/cart-warnings
- Omitting the Buyer-IP header on private-token calls has three documented effects, not just throttling: it "can result in throttled API requests, limited bot protection, and unauthenticated flows at checkout." The header is documented only for private-token requests; nothing is said for tokenless or public-token server calls.
  Source: https://shopify.dev/docs/api/storefront/latest
- Local-currency pricing through buyerIdentity.countryCode or @inContext(country:) only works for currencies enabled on the checkout store: the pricing guide lists as a requirement that each country's currency be enabled manually in the store's payment settings, and "Any queries for countries that aren't enabled will default to the store currency."
  Source: https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/markets/international-pricing
- Policy constraints from the Shopify API License and Terms of Use (section numbers as rendered by the fetch reader): apps must "not attempt to circumvent such limitations" (API rate limits, s.2.4) and must not "use an alternative to Shopify Checkout for checkout or payment processing" (s.2.3.18). The design complies as long as it redirects to Shopify Checkout and forwards the buyer's genuine IP (never a fabricated or rotated one).
  Source: https://www.shopify.com/legal/api-terms
- The 100-token limit is worded inconsistently: the StorefrontAccessToken object says "An app can have a maximum of 100 active storefront access tokens for each Shop", while the storefrontAccessTokenCreate mutation page says each shop can have up to 100 active StorefrontAccessToken objects. Either way, mint one token per store and reuse it (list existing tokens before creating) instead of minting on every Admin-token refresh.
  Source: https://shopify.dev/docs/api/admin-graphql/latest/mutations/storefrontAccessTokenCreate
