# Arquitetura do checkout-bridge

Este documento descreve o que o código faz e por quê. As referências entre colchetes ([SF-15], [AC-64] etc.) apontam para `docs/research/`, pesquisa conferida contra a documentação da Shopify em 2026-10-05. Onde a Shopify não documenta um comportamento, o texto diz que ele precisa de teste em loja real: o código não foi executado contra uma loja de verdade.

## 1. Componentes

```
navegador do comprador                 Shopify                          checkout-bridge
┌─────────────────────┐   POST /apps/checkout-bridge/checkout   ┌──────────────────────────┐
│ tema da vitrine     │ ──────────────► App Proxy ────────────► │ /proxy  (routes/proxy)   │
│ + bridge.client.js  │ ◄────────────── 200 JSON ◄───────────── │   assinatura, limites    │
│                     │                                          │   checkout/service       │
│  location.assign ───┼──► checkout da loja checkout            │     ├─ catalog (cache)    │
└─────────────────────┘                                          │     ├─ mappings           │
                                                                 │     └─ shopify/storefront ├──► Storefront API (cartCreate)
         Shopify ──── webhooks products/* ─────────────────────► │ /webhooks (routes/webhooks)
                                                                 │   catalog/queue → sync    ├──► Admin API (GraphQL)
         lojista ──── navegador ──────────────────────────────► │ /admin  (painel)          │
         monitoramento ───────────────────────────────────────► │ /healthz /readyz /metrics │
                                                                 │ SQLite (data/bridge.db)   │
                                                                 └──────────────────────────┘
```

| Componente | Arquivos | Papel |
| --- | --- | --- |
| Script do tema | `src/theme/bridge.client.js`, `src/theme/render.ts` | Roda no navegador do comprador. Intercepta o clique de finalizar compra, salva o formulário do carrinho (`cart/update.js`), lê `cart.js`, envia variantes e quantidades ao serviço pelo App Proxy e navega para a URL devolvida. Esconde botões de checkout acelerado. |
| Rota do proxy | `src/routes/proxy.ts`, `src/shopify/proxy-signature.ts` | Verifica a assinatura do App Proxy, resolve a loja vitrine pelo parâmetro `shop` assinado, aplica limites de taxa por IP e por loja, valida o corpo e chama o serviço de checkout. Serve também `/ping` e `/bridge.js`. Responde sempre 200 com JSON. |
| Serviço de checkout | `src/checkout/*` | Resolve a rota, traduz variantes pelo mapeamento, aplica limites, confere disponibilidade e paridade pelo catálogo em cache, garante idempotência, cria o carrinho (ou permalink), confere o carrinho devolvido e grava a sessão. |
| Clientes Shopify | `src/shopify/auth.ts`, `admin.ts`, `storefront.ts`, `webhook-hmac.ts` | Token da Admin API (client credentials, 24 h, renovação antecipada, emissão serializada por loja), GraphQL Admin com controle de custo e `THROTTLED`, `cartCreate` na Storefront API com timeout, retry e circuit breaker por loja, verificação de HMAC de webhooks. |
| Catálogo | `src/catalog/*` | Sincronização completa paginada do catálogo (produtos, variantes, preço de catálogo, estoque), releitura de produto por webhook, casamento de variantes, cálculo de divergências, registro de webhooks, fila em memória com agrupamento, conexão de loja (relatório em cinco etapas). |
| Banco | `src/db/*` | SQLite via `node:sqlite`, modo WAL, migrações versionadas, repositórios. Segredos cifrados (AES-256-GCM, chave `ENCRYPTION_KEY`) antes de gravar. |
| Painel | `src/routes/admin/*`, `src/admin/auth.ts` | Lojas, rotas, mapeamentos, sessões de checkout e auditoria. Senha única, sessão em cookie `HttpOnly; SameSite=Strict` (o banco guarda um HMAC do token com chave derivada da senha: trocar `ADMIN_PASSWORD` invalida todas as sessões abertas), CSRF por token, CSP restritiva. |
| Operação | `src/routes/health.ts`, `src/lib/metrics.ts`, `src/lib/alerts.ts`, `src/lib/logger.ts` | `/healthz`, `/readyz`, `/metrics` (Prometheus, com token opcional), alertas para webhook com deduplicação, log JSON com censura de segredos. |

## 2. Fluxo da requisição: do clique ao redirecionamento

1. **Clique.** O script captura o `submit` do formulário de carrinho com botão `name="checkout"` (ou um link para `/checkout`, ou um botão de compra direta), cancela o envio nativo e trava o botão.
2. **Carrinho.** Envia a `cart/update.js` só os campos `note`, `attributes[...]` e `updates[...]` do formulário (para persistir nota, atributos e quantidades editadas; qualquer outro campo, como um `discount` em branco, não é reenviado), lê `cart.js` e monta a carga: para cada item, `variant_id`, `quantity`, propriedades (menos as privadas `__x`) e `hasSellingPlan`; mais `cartToken` (sem a chave `?key=`), país e idioma do contexto da loja, cupons que o carrinho diz aplicáveis, parâmetros de atribuição guardados (utm_*, fbclid, gclid, ttclid...), consentimento lido da Customer Privacy API e `clientNonce` (nonce aleatório gerado uma vez por aba, ver §6 Idempotência). Preço não entra [AJ-04, PT-25].
3. **App Proxy.** `POST https://<vitrine>/apps/checkout-bridge/checkout`, mesma origem, sem query string própria. A Shopify encaminha para `https://<serviço>/proxy/checkout` e acrescenta na query `shop`, `path_prefix`, `timestamp`, `logged_in_customer_id` e `signature` [SC-49].
4. **Autenticação.** O serviço lê o `shop` ainda não verificado só para achar a loja e o segredo dela, recalcula o HMAC-SHA256 hex sobre todos os parâmetros menos `signature` (valores decodificados, chaves repetidas unidas por vírgula, pares ordenados, concatenados sem separador) [SC-51, SC-52], compara em tempo constante, rejeita `shop`/`timestamp`/`signature` duplicados e `timestamp` fora da janela (`PROXY_SIGNATURE_MAX_AGE_SECONDS`, padrão 90 s, o mesmo da biblioteca oficial). Só então o `shop` assinado define a vitrine. A assinatura não cobre o corpo [SC-57]: ele é dado não confiável.
5. **Limites.** Balde por `shop:IP` (`RATE_LIMIT_PER_IP_PER_MINUTE`) e por `shop` (`RATE_LIMIT_PER_SHOP_PER_MINUTE`). Corpo limitado a 64 KB, `Content-Type` obrigatório `application/json`, esquema estrito (chave desconhecida como `price` invalida a requisição).
6. **Rota.** Entre as rotas ativas da vitrine, vence a `country` que lista o país do comprador; senão a `default`; sem nenhuma, erro `no_route` e alerta. Nenhum outro critério [`src/checkout/routing.ts`].
7. **Limites da rota e assinatura.** Até 100 linhas (teto rígido) e `maxQuantityPerLine` por linha e também para o **total por variante da loja checkout**, somando todas as linhas que caem nela, com ou sem propriedades: dividir a quantidade em várias linhas (iguais ou distinguidas só por uma propriedade) não escapa do limite. Um carrinho legítimo com a mesma variante personalizada de vários jeitos (3 "Ana" + 3 "Bia") precisa de `maxQuantityPerLine` >= 6 na rota. Linha com plano de assinatura é recusada (`selling_plan_unsupported`).
8. **Catálogo e mapeamento.** Toda variante precisa existir no catálogo sincronizado da vitrine (um ID inventado para aqui) e ter mapeamento `active` com destino; o destino precisa existir no catálogo sincronizado da loja checkout, estar com produto `ACTIVE` ou `UNLISTED`, `availableForSale` e, se o estoque é rastreado com política `DENY`, com quantidade suficiente para o total pedido.
9. **Paridade em cache.** Com política diferente de `off`, compara moeda e preço de catálogo das duas variantes dentro da tolerância da rota. `block` recusa (`price_divergence`) e alerta; `warn` registra métrica e segue.
10. **Idempotência.** Chave SHA-256 de (vitrine, rota, origem, token do carrinho ou escopo de reserva, país, cupons, linhas canônicas). Se já existe sessão viva com a chave (criada e não expirada, ou pendente há menos de 60 s), a requisição espera até 3 s por ela e devolve a mesma URL; senão insere uma sessão `pending` de forma atômica. Se a sessão esperada terminar em falha, quem esperava recebe o mesmo código (`price_divergence`, `quantity_exceeded`...), exceto falhas transitórias (`internal`, `upstream_unavailable`, `conflict`, `not_found`, `rate_limited`), que viram `upstream_unavailable` para o comprador tentar de novo.
11. **Criação.** Estratégia `storefront_cart`: `cartCreate` na loja checkout com `merchandiseId` + `quantity` (+ atributos de linha para propriedades), atributos de carrinho `bridge_session`, `bridge_source` e os de atribuição, `buyerIdentity.countryCode`, cupons, `@inContext(language, visitorConsent)`, e, com token privado, `Shopify-Storefront-Buyer-IP`. Estratégia `permalink`: monta `https://<checkout>/cart/<id>:<qtd>,...?attributes[...]&discount=` na mesma loja. Indisponibilidade da Storefront API (rede, timeout, circuito aberto) com `allowPermalinkFallback` cai no permalink **da mesma loja checkout**; recusa da Shopify não.
12. **Conferência do carrinho.** `userErrors` vazio não basta [SF-15]: o serviço compara, variante a variante, a quantidade devolvida com a pedida, trata `warnings` de estoque (`MERCHANDISE_OUT_OF_STOCK`, `MERCHANDISE_NOT_ENOUGH_STOCK`, `PRODUCT_UNAVAILABLE_IN_BUYER_LOCATION`), linhas com `availableForSale: false`, linhas que ninguém pediu e variantes que sumiram sem aviso (sinal de produto não publicado no canal [SF-17]; gera alerta crítico). Depois compara o preço unitário que a loja checkout vai cobrar com o preço da vitrine, na mesma moeda; moeda diferente não é comparada (métrica `bridge_checkout_parity_skipped_total`).
13. **Resposta.** Acrescenta `utm_*` à URL do checkout sem reescrever a query existente (ela carrega a chave do carrinho e o consentimento `_cs`), confere que a URL final é https e está no host da loja checkout (ver §6; outro host recusa com `upstream_rejected`, `reason: checkout_url_host`), grava a sessão como `created` (id do carrinho sem a chave; a URL completa fica guardada enquanto a sessão vale para a idempotência e é apagada pelo expurgo diário depois que ela expira) e responde `200 {ok: true, checkoutUrl, sessionId}`. O script faz `location.assign(checkoutUrl)`. Erros respondem `200 {ok: false, code, message}` com mensagem segura para o comprador; o motivo detalhado fica no log e, quando cabe, em alerta. Responder 3xx ou 4xx/5xx pelo proxy não é confiável [SC-66, RISK-03].

Em paralelo, webhooks `products/*` entram por `/webhooks/shopify`: HMAC base64 do corpo cru com o segredo da loja identificada por `X-Shopify-Shop-Domain` [AC-61], deduplicação por id de entrega, e o produto é **relido** pela Admin API numa fila com agrupamento de 5 s (o corpo do webhook pode vir incompleto [AC-68]). Depois de mudanças, o mapeamento do par é recalculado (10 s de agrupamento; enquanto a loja ainda relê produtos o recálculo é adiado, no máximo 5 vezes seguidas, ou seja, até 60 s, e então roda mesmo com releituras em curso). Releitura de produto e ressincronização completa da mesma loja nunca correm ao mesmo tempo: cada uma espera a outra terminar, e um produto removido por webhook durante a ressincronização não volta por uma página lida antes da remoção. `app/uninstalled` marca a loja em erro, invalida o token e alerta.

## 3. Modelo de dados

Tabelas em `src/db/schema.ts` (SQLite, datas ISO 8601 UTC, IDs da Shopify como texto):

| Tabela | Conteúdo | Observações |
| --- | --- | --- |
| `stores` | Loja: papel (`vitrine`/`checkout`), nome, `shop_domain`, domínio público, caminho do proxy, Client ID, **Client secret cifrado**, moeda, status (`pending`/`connected`/`error`/`disabled`), modo e **token de Storefront cifrado**, última sincronização. | Segredos em claro nunca são gravados nem devolvidos. |
| `links` | Rota vitrine → checkout: tipo (`default`/`country`), países, ativa, política de paridade, tolerância em pontos-base, limites de quantidade e linhas, estratégia, permalink de reserva. | Índice único parcial garante uma `default` ativa por vitrine; a regra dos países fica na transação do repositório. Somem com a loja. |
| `catalog_variants` | Cópia do catálogo de cada loja: produto (id, título, handle, status), variante (id, título, opções, SKU, código de barras, preço de catálogo, preço comparativo, moeda da loja, disponível, política e quantidade de estoque, rastreado), `synced_at`. | Preço na moeda padrão da loja (`ProductVariant.price`) [AC-08]. Produtos `DRAFT`/`ARCHIVED` também entram; quem decide o que é vendável é o consumidor. |
| `variant_mappings` | Por par (vitrine, checkout, variante da vitrine): variante de destino, status, método, candidatos (conflito), divergências, `locked`. | Decisões manuais são travadas e preservadas pelo casamento automático. |
| `checkout_sessions` | Cada tentativa de checkout: chave de idempotência, lojas, rota, status (`pending`/`created`/`failed`), estratégia, linhas (variante vitrine → checkout, quantidade), país, URL do checkout (apagada quando a sessão expira), id do carrinho **sem a chave**, subtotal, moeda, código de erro, HMAC do IP, expiração. | Sem chave estrangeira para lojas: o histórico sobrevive à remoção da loja. Expurgado por `RETENTION_DAYS`. |
| `audit_log` | Ações do painel, do sistema e de webhooks: ator, ação, alvo, detalhe sem segredos nem dados pessoais. | |
| `webhook_events` | Ids de entrega já vistos, para descartar repetições. | |
| `admin_sessions` | Sessões do painel: **hash** do token do cookie, token CSRF, expiração (12 h). | Uma cópia do banco não permite assumir uma sessão. |
| `job_runs` | Última execução concluída de cada tarefa periódica (`catalog_resync`). | Faz o agendamento da ressincronização sobreviver a reinícios do processo. |

### Pedidos (vendas)

A tabela `orders` guarda, por loja, o essencial de cada pedido vindo dos webhooks `orders/create`, `orders/updated`, `orders/cancelled` e `refunds/create`: id, número, data, moeda, subtotal, total, total reembolsado, status financeiro, cancelamento, quantidade de itens, a sessão da ponte (atributo `bridge_session`) e a vitrine de origem. Nada do comprador é gravado. Pedidos com `test = true` são ignorados. A receita do painel é total menos reembolsos dos pedidos não cancelados, somada por moeda e por dia em UTC; pedidos de lojas vitrine contam como "fora da ponte" e geram alerta.

## 4. De onde vem o preço e as três conferências

O preço nunca entra pelo navegador. O script envia só variante e quantidade; o esquema de validação recusa qualquer chave desconhecida no corpo, inclusive `price`. Na Storefront API, `CartLineInput` não tem campo de preço [SF-08]: a loja checkout precifica cada linha pelo próprio catálogo, no contexto de `buyerIdentity.countryCode` [PT-01, PT-02]. Isso é o que garante que o comprador paga o preço da loja checkout.

O que o serviço faz é conferir, em três momentos, que esse preço é o que a vitrine mostrou:

1. **Paridade em cache** (antes de falar com a Shopify). Compara o preço de catálogo (`ProductVariant.price`, moeda padrão de cada loja [AC-08]) da variante da vitrine com o da variante de destino, dentro da tolerância da rota. Também alimenta as divergências mostradas no painel. É rápida e pega o caso comum: preço esquecido numa das lojas.
2. **Conferência ao vivo** (sobre o carrinho criado). Lê `lines[].cost.amountPerQuantity` [SF-19] devolvido pela loja checkout e compara com o preço da vitrine, na mesma moeda. Pega o que o cache não vê: preço por mercado, desconto automático aplicado só de um lado, catálogo em cache desatualizado. Moeda diferente da vitrine (comprador de outro mercado) não é comparada, porque não há base sem câmbio; fica na métrica.
3. **O checkout da Shopify** é a autoridade final. O custo do carrinho é declaradamente uma estimativa [SF-18, PT-21]: impostos e frete só existem no checkout [PT-66], e o checkout pode trocar moeda e preços se o endereço de entrega for de outro país [PT-19]. O serviço garante o preço unitário das linhas para o país informado; o total final é do checkout.

A plataforma não garante paridade de preço entre duas lojas [PT-09 a PT-20]: câmbio ao vivo, taxa de conversão embutida, arredondamento, ajustes percentuais por mercado e descontos automáticos de uma loja só são fontes documentadas de diferença. A configuração mais determinística é a mesma moeda padrão nas duas lojas, a mesma estrutura de mercados e preços fixos por mercado (preço fixo em lista de preços não passa por câmbio nem arredondamento [PT-11]).

## 5. Estratégia de mapeamento

O serviço mantém uma **tabela de mapeamento no próprio banco** (`variant_mappings`), preenchida por casamento automático com **SKU em primeiro lugar** e corrigível à mão. Alternativas consideradas:

| Estratégia | A favor | Contra |
| --- | --- | --- |
| **Tabela própria, SKU primeiro, depois código de barras, handle+opções e título+opções** (escolhida) | SKU é o identificador que o lojista já controla e costuma repetir entre lojas; a tabela guarda decisões manuais, candidatos em conflito e divergências; o checkout consulta só o banco local (rápido e sem depender da Shopify no clique); o painel mostra tudo o que precisa de revisão; as regras mais fracas só sugerem, nunca vendem o produto errado em silêncio. | Exige disciplina de SKU nas duas lojas; SKU repetido vira conflito a resolver à mão; a tabela precisa ser recalculada quando o catálogo muda (feito por webhook e pela ressincronização). |
| Metafields na Shopify (gravar na variante da vitrine o id da variante do checkout) | Dado fica na própria loja; sobrevive a este serviço. | Exige escopo de escrita na loja (o serviço só lê, de propósito); ler metafields no clique custaria uma chamada à Admin API por checkout ou uma sincronização igual à atual; não há lugar natural para conflitos, sugestões e divergências; trocar a loja checkout de uma rota exigiria regravar todas as variantes. |
| Só código de barras | Identificador global (EAN/GTIN) quando existe. | Muitos catálogos não têm código em todas as variantes; a Shopify descontinuou `ProductVariant.barcode` na 2026-10 em favor de `barcodes` (até 20 por variante), e o campo antigo devolve só o primeiro [AC-05]; produtos próprios sem GTIN ficariam sem mapeamento. Fica como segunda regra. |
| Título (+ opções) | Funciona sem nenhum identificador. | Títulos mudam com marketing, traduções e variações de grafia; dois produtos de mesmo nome são indistinguíveis; casar por título em silêncio é o jeito mais fácil de vender o item errado. Por isso é a última regra e só gera **sugestão**, que alguém aprova no painel. |

Detalhes do casamento (`src/catalog/match.ts`, `parity.ts`): SKU e código de barras comparam exatamente (a Shopify diferencia maiúsculas), só sem espaços nas pontas; com vários candidatos de mesmo código, as opções desempatam; sem desempate é conflito. Handle e título passam por normalização Unicode e de espaços, e as opções entram ordenadas (a ordem das opções no produto não importa; "Title = Default Title" equivale a nenhuma opção). Variantes do checkout em rascunho ou arquivadas também são candidatas: casar e marcar a divergência "status do produto" informa mais do que "sem destino". Divergências são recalculadas a cada casamento com a menor tolerância entre as rotas do par. Decisões manuais ficam travadas e sobrevivem ao recálculo, inclusive quando o produto da vitrine sai do ar temporariamente.

## 6. Modelo de segurança

- **Autenticação entre tema e serviço.** Toda requisição do navegador passa pelo App Proxy e chega com assinatura HMAC-SHA256 da Shopify sobre a query string, calculada com o Client secret do app da vitrine. O serviço recalcula sobre **todos** os parâmetros recebidos (a Shopify pode acrescentar novos [SC-56]), compara em tempo constante, recusa `shop`, `timestamp` e `signature` repetidos e usa o `shop` assinado para decidir a loja; nenhum campo do corpo decide nada de identidade. O proxy não repassa cookies em nenhum sentido [SC-62], então não há sessão de comprador. Um `shop` desconhecido, de loja checkout ou desativada é recusado antes de qualquer processamento.
- **Validação de entrada.** Corpo até 64 KB, `Content-Type: application/json` obrigatório, esquema `zod` estrito: linhas com id numérico e quantidade inteira positiva, no máximo 250 linhas na forma (100 no serviço), propriedades limitadas em número e tamanho (limites em `src/checkout/limits.ts`, os mesmos que o script do tema aplica antes de enviar: uma personalização longa demais vira mensagem ao comprador, nunca um corte silencioso), até 5 cupons, atribuição só por lista de permissão, país e idioma com formato fixo, caracteres de controle rejeitados. As mensagens de erro nunca repetem o valor recebido.
- **Limites de taxa.** Balde de fichas por `loja:IP` do comprador (padrão 20/min) e por loja (padrão 600/min), nessa ordem, para um comprador insistente não gastar a cota da loja. `/bridge.js` não é limitado: recusar o script deixaria o comprador no checkout nativo da vitrine. Login do painel é limitado por IP (5 por minuto) e, como reserva para IPs forjados ou desconhecidos, por um balde global de 30 tentativas por minuto somando todos os IPs; o balde do IP é consumido primeiro, para um IP insistente não trancar o painel para os demais, e só tentativas que passam pelos dois limites vão para a auditoria. O IP do cliente vem de `X-Forwarded-For` contado **a partir da direita** por `TRUSTED_PROXY_HOPS` (nas rotas do proxy, um salto a mais pela própria Shopify [SC-61]); o item mais à esquerda, que o próprio cliente escreve, nunca é usado, e sem item válido vale `X-Real-IP` ou nenhum IP.
- **Janela de replay.** O `timestamp` assinado precisa estar dentro de `PROXY_SIGNATURE_MAX_AGE_SECONDS` (padrão 90 s, valor da biblioteca oficial da Shopify [SC-69, correção]). Uma requisição capturada e repetida depois disso é recusada.
- **Idempotência.** Chave derivada do carrinho (token do carrinho da vitrine ou, sem ele, o nonce do navegador enviado pelo script + janela de 10 s; sem nonce, IP em hash + User-Agent + janela), rota, país, cupons e linhas. Clique duplo, nova tentativa do script e duas abas com o mesmo carrinho reaproveitam o mesmo checkout dentro de `SESSION_TTL_MINUTES`; a inserção da sessão pendente é atômica, e uma requisição concorrente espera a primeira em vez de criar outro carrinho. O nonce (`clientNonce`, 8..64 caracteres de `[A-Za-z0-9_-]`) é gerado uma vez por aba pelo script (`crypto.randomUUID`, guardado em `sessionStorage` sob `cb_nonce`; só em memória quando o armazenamento falha), não identifica o comprador e entra apenas na chave.
- **URL final só na loja checkout.** Antes de responder, o serviço confere que a URL de checkout é https e que o host é o domínio canônico `xxx.myshopify.com` da loja checkout, o domínio público cadastrado ou, enquanto não há domínio público, qualquer `*.myshopify.com`. Outro host (resposta adulterada, configuração errada) recusa com `upstream_rejected` (`reason: checkout_url_host`), marca a sessão como falha e alerta o lojista; o comprador nunca é redirecionado para fora da loja checkout.
- **Adulteração de preço e de variante.** Preço não é aceito (esquema estrito) e não existe na API [SF-08]. Um id de variante que não está no catálogo sincronizado da vitrine, ou que não tem mapeamento ativo, é recusado; o destino é sempre o da tabela de mapeamento, nunca um id vindo do navegador. Depois do `cartCreate`, linhas inesperadas no carrinho fazem o checkout ser recusado com alerta.
- **Abuso de quantidade.** Limite por linha e por checkout configurados na rota, aplicados também depois de fundir linhas da mesma variante (dividir a quantidade em várias linhas não passa). Estoque é conferido no cache (política `DENY`) e ao vivo (avisos de estoque e quantidade devolvida diferente da pedida [SF-15, PT-83]).
- **Sem CORS.** A chamada do tema é de mesma origem (domínio da vitrine, via proxy). O serviço não emite cabeçalho `Access-Control-Allow-Origin`: emiti-lo abriria a rota para outras origens.
- **CSRF no painel.** Sessão em cookie `HttpOnly; SameSite=Strict; Path=/admin` (e `Secure` em https); todo POST leva um token CSRF ligado à sessão, comparado em tempo constante; CSP `default-src 'none'` com script e estilo só do próprio serviço, `form-action 'self'`, `frame-ancestors 'none'`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`.
- **Segredos cifrados em repouso e nunca enviados ao navegador.** Client secret e token de Storefront são cifrados com `ENCRYPTION_KEY` antes de ir ao banco; o painel nunca os devolve (campo vazio = manter). O id do carrinho da Shopify tem o formato `<token>?key=<segredo>` [SF-23]: só o token é guardado. A URL do checkout devolvida ao navegador é a que a própria Shopify emitiu para aquele comprador; ela leva a chave, por isso fica no banco só enquanto a sessão vale para a idempotência (`SESSION_TTL_MINUTES`) e é apagada pelo expurgo diário depois disso.
- **Log sem dados pessoais.** O IP do comprador só existe em memória para limitar taxa e para o cabeçalho `Shopify-Storefront-Buyer-IP`; no banco fica um HMAC com chave derivada de `ENCRYPTION_KEY`. O logger censura por nome de campo (`clientSecret`, `token`, `password`, `buyerIp`, `encryptionKey`, `alertWebhookUrl`...); query string do proxy, corpo das requisições e URL de checkout não são logados; alertas passam pela mesma censura antes de sair para o webhook. E-mail, endereço e nome do comprador nunca passam pelo serviço.
- **Timeouts.** Toda chamada à Shopify tem tempo limite (`UPSTREAM_TIMEOUT_MS`, padrão 6 s) e o corpo é lido dentro dele. No navegador, o script espera no máximo 12 s pela resposta do proxy e 8 s pelo carrinho, e depois libera o botão.
- **Retry com backoff.** Admin API: até 3 novas tentativas em falha transitória e até 5 em `THROTTLED`, esperando o que `extensions.cost.throttleStatus` indica [AC-28, AC-29]; token: até 2 novas tentativas, com erros permanentes (`shop_not_permitted`, `application_cannot_be_found`...) lembrados por 30 s para não martelar a loja. Storefront: só falhas de rede, timeout e 5xx são repetidas; recusa da Shopify (userErrors, 401/403, 430) não. `userErrors` com `CartErrorCode` determinístico para o mesmo carrinho viram o código de negócio próprio e geram alerta ao lojista (`MAXIMUM_EXCEEDED`, `MINIMUM_NOT_MET`, `INVALID_INCREMENT` → `quantity_exceeded`; `VARIANT_REQUIRES_SELLING_PLAN`, `SELLING_PLAN_NOT_APPLICABLE` → `selling_plan_unsupported`; `MERCHANDISE_NOT_APPLICABLE`, `INVALID_MERCHANDISE_LINE` → `variant_unavailable`; `VALIDATION_CUSTOM`, de uma Function de validação de checkout, → `checkout_validation`); os demais continuam `upstream_rejected`.
- **Circuit breaker.** Por loja checkout, na Storefront API: depois de 5 falhas seguidas de disponibilidade o circuito abre por 30 s, as chamadas falham rápido com `upstream_unavailable` e um alerta crítico é emitido; passado o tempo, uma chamada de teste decide se ele fecha de novo. **O circuito nunca escolhe outra loja**: significa só que o checkout daquela loja está fora do ar.
- **Métricas.** Contadores e histogramas Prometheus em `/metrics` (com `METRICS_TOKEN` opcional), com teto de séries para um rótulo fora de controle não esgotar memória; rótulos vindos de fora (tópico de webhook, código de erro) são normalizados para listas fixas.
- **Alertas.** `Alerter.notify` nunca lança nem bloqueia; deduplicação por chave por 5 minutos; envio em segundo plano com tempo limite e teto de envios simultâneos; detalhe censurado.
- **Auditoria.** Login/logout e falhas de login (sem senha nem IP), criação, edição, conexão, sincronização, ativação e remoção de lojas e rotas, decisões de mapeamento, testes de rota, desinstalação por webhook. Sem segredos e sem dados pessoais.

## 7. As duas estratégias de checkout

| | `storefront_cart` (padrão) | `permalink` |
| --- | --- | --- |
| Como funciona | `cartCreate` na Storefront API da loja checkout; o serviço recebe o carrinho de volta e redireciona para `cart.checkoutUrl`. | Monta `https://<checkout>/cart/<variante>:<qtd>,...` [PL-01] e redireciona; a Shopify monta o carrinho ao abrir o link. |
| O que é conferido no clique | Linhas, quantidades, estoque, publicação (indiretamente) e preço unitário real. | Nada além do catálogo em cache: a Shopify não devolve nada ao servidor. |
| País e idioma | `buyerIdentity.countryCode` e `@inContext(language)` [SF-51, verificador]. | Idioma só por prefixo de caminho (não implementado); país e moeda não têm parâmetro documentado [PL-10]. |
| Propriedades de linha | Como atributos da linha do carrinho. | Só para o primeiro produto, em um único parâmetro [PL-03]; o serviço recusa permalink quando há propriedades. |
| Consentimento | `@inContext(visitorConsent)` codificado na URL do checkout (`_cs`) [AT-21, correção]. | Não há equivalente documentado. |
| Atribuição | Atributos do carrinho (`bridge_session`, `bridge_source`, utm_*, click ids, cookies de pixel) e utm_* na URL. | `attributes[...]` na URL [PL-06], sem os valores de cookies (a URL passa por redirecionamentos, logs e Referer). |
| Cupons | `discountCodes`; o serviço vê `applicable` e avisos de desconto. | `?discount=a,b` [PL-05]; códigos com vírgula não cabem. |
| Dependência no clique | Storefront API da loja checkout respondendo. | Nenhuma chamada à Shopify. |
| Tamanho | Até 100 linhas (teto do serviço). | Limite de URL não documentado; o serviço corta em 8.000 caracteres e remove a atribuição antes de desistir. |

**Quando usar cada uma.** `storefront_cart` é a escolha para a operação normal: é a única que confere o que a loja checkout vai cobrar e em que quantidade antes de mandar o comprador. `permalink` serve para rotas em que a Storefront API da loja checkout não pode ser usada (modo sem token bloqueado com 430 e sem token privado disponível, por exemplo) e como **reserva** da estratégia principal (`allowPermalinkFallback`), só para indisponibilidade da API e sempre na mesma loja checkout. Em qualquer dos casos a loja checkout não pode estar protegida por senha [PL-11] e as linhas não podem ter plano de assinatura [PL-11].

## 8. Limitações

**Descontos e descontos automáticos.** Cupons são objetos da loja checkout: um código da vitrine só funciona se existir também lá [PT-37]. O serviço encaminha até 5 códigos que o carrinho da vitrine diz aplicáveis; a Shopify devolve `applicable` e avisos (`DISCOUNT_NOT_FOUND` etc.) sem falhar a mutação [PT-31 a PT-34], e o serviço só registra. Descontos automáticos da loja checkout se aplicam sem nenhuma entrada e não podem ser desligados por canal [PT-36]; descontos automáticos da vitrine não se transferem. Resultado: o total do checkout pode diferir do total que a vitrine mostrou mesmo com preços iguais. Fonte: https://help.shopify.com/en/manual/discounts/sales-channel-discounts e https://shopify.dev/docs/api/storefront/latest/enums/CartWarningCode.

**Preço comparativo ("de/por").** O painel marca como divergência quando `compareAtPrice` existe só de um lado ou difere; não bloqueia o checkout. O que o comprador vê no checkout é o da loja checkout [SF-19]. Fonte: https://shopify.dev/docs/api/storefront/latest/objects/CartLineCost.

**Planos de venda e assinaturas (não suportados).** Linha com `selling_plan_allocation` na vitrine é recusada (`selling_plan_unsupported`). Planos de venda são por loja, exigiriam mapeamento próprio e o escopo `unauthenticated_read_selling_plans` [PT-50, PT-51], e o permalink não os transporta [PL-11]. Fonte: https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/products-collections/subscriptions e https://shopify.dev/docs/apps/build/checkout/create-cart-permalinks.

**Bundles.** Não há tratamento especial. A publicação de bundles para storefronts personalizados é desligada por padrão e exige converter o app em canal de vendas; se isso vale para um app do Dev Dashboard não é documentado [PT-58, correção]. Variantes com `requiresComponents` somem de canais sem suporte a bundles [PT-59]. Precisa de teste em loja real antes de vender bundles pela ponte. Fonte: https://shopify.dev/docs/apps/build/product-merchandising/bundles/turn-on-publishing.

**Vales-presente.** Um vale emitido pela vitrine não é resgatável na loja checkout; não existe transferência entre lojas [PT-54, PT-55]. Venda e aceite vales só na loja checkout, ou não os venda pela ponte. Fonte: https://help.shopify.com/en/manual/products/gift-card-products/overview.

**Impostos e frete.** Não existem no carrinho da Storefront API; são calculados no checkout da loja checkout, com as configurações fiscais e de envio dela [PT-66, PT-67]. A vitrine não deve prometer valores de frete ou imposto. Fonte: https://shopify.dev/changelog/tax-and-duties-are-deprecated-in-storefront-cart-api.

**Moeda e Markets.** O preço vem do mercado da loja checkout para o país informado; país não habilitado lá cai na moeda padrão da loja [PT-05]; cobrar em moeda local exige Shopify Payments ou Adyen [PT-17]; o checkout pode trocar a moeda se o endereço de entrega for de outro país [PT-19]. O catálogo em cache compara só preços na moeda padrão de cada loja; quando o carrinho volta em moeda diferente da vitrine, o preço não é comparado. Vitrine e checkout com moedas padrão diferentes geram divergência de moeda em todas as linhas. Fonte: https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/markets/international-pricing e https://help.shopify.com/en/manual/international/pricing/checkout-restrictions.

**Contas de cliente e login.** A sessão do cliente na vitrine não atravessa para a loja checkout: são lojas diferentes, com clientes diferentes, e cookies não cruzam domínios registráveis distintos [CO-01, CO-02]. O comprador entra no checkout da loja checkout como visitante (ou com a conta que tiver lá). `logged_in_customer_id` do proxy é ignorado. Fonte: https://shopify.dev/docs/api/customer-privacy.

**Carrinho deixado na vitrine.** O serviço não esvazia o carrinho da vitrine depois da compra (não há como saber, do navegador da vitrine, que o pedido foi concluído na outra loja; `cart/clear.js` mantém atributos e nota [AJ-15]). O comprador que voltar à vitrine verá o carrinho antigo. Fonte: https://shopify.dev/docs/api/ajax/reference/cart.

**Atribuição e pixels em dois domínios.** Cookies de analytics e de pixels da vitrine não existem na loja checkout; o serviço leva utm_* e click ids (fbclid, gclid, ttclid...) como atributos do carrinho e utm_* na URL, e lê os cookies `_fbp`, `_fbc`, `_ga`, `_ttp` para enviá-los como atributos. Que atributos do carrinho cheguem ao pedido e aos eventos de pixel do checkout, e que utm_* na URL cheguem a `customerJourneySummary`, é inferência, não documentação [AT-14, AT-16, correções]: precisa de teste com pedido real. Relatórios de conversão da loja checkout tendem a mostrar "Direct" [AT-07]. Pixels devem ser instalados na loja checkout. Fonte: https://shopify.dev/docs/api/web-pixels-api/standard-events/checkout_started e https://help.shopify.com/en/manual/reports-and-analytics/discrepancies/customer-discrepancies.

**Consentimento.** O consentimento dado na vitrine é lido pela Customer Privacy API e enviado em `@inContext(visitorConsent)`, que a Shopify codifica na URL do checkout (desde 2025-10) [AT-21, correção]. Isso não existe no permalink. Em regiões que exigem consentimento, pixels da loja checkout podem ficar suprimidos até o consentimento ser registrado lá. Fonte: https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/in-context.

**E-mails de carrinho abandonado.** O carrinho existe só na loja checkout; os e-mails de recuperação são os dela, com o domínio e a marca dela. A vitrine não tem checkout iniciado para recuperar. Carrinhos não usados expiram em até 30 dias [SF-24]. Fonte: https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/cart.

**Lojas protegidas por senha.** Permalinks não passam pela senha da loja virtual [PL-11] e há relato de `checkoutUrl` da Storefront API parando na página de senha (não oficial). O comportamento de requisições ao App Proxy numa vitrine com senha não é documentado [SC-67]; há relato de redirecionamento para a página de senha. A loja checkout não pode usar a senha da loja virtual; a vitrine com senha precisa de teste em loja real. Fonte: https://shopify.dev/docs/apps/build/checkout/create-cart-permalinks e https://shopify.dev/docs/apps/build/checkout/capabilities.

**Publicação dos produtos no canal da Storefront.** A Storefront API só devolve produtos publicados no canal que o token resolve e no mercado consultado [SF-53]; produto não publicado parece apagado [SF-54], e há relato de a variante simplesmente sumir do carrinho sem erro [SF-17]. Qual publicação o acesso sem token usa não é documentado. O serviço detecta o sumiço na conferência do carrinho e alerta, mas não consegue prever pelo cache (ele não lê publicação). Publique os produtos da loja checkout no canal correspondente (Loja virtual ou Headless) e use o teste de rota. Fonte: https://shopify.dev/docs/api/storefront/latest/queries/product.

**Botões de checkout acelerado.** Não podem ser interceptados (shadow DOM fechado, sem API) [CK-11, CK-12]; levam ao checkout da vitrine [CK-14]. O script os esconde por CSS, mas o lojista precisa desligá-los no tema (instruções em `docs/INSTALACAO.md`, seção 7.2). Fonte: https://shopify.dev/docs/storefronts/themes/pricing-payments/accelerated-checkout.

**Clique duplo sem token do carrinho.** A idempotência usa o token do carrinho da vitrine; quando ele não existe (compra direta), o escopo de reserva é o nonce do navegador enviado pelo script + janela de 10 s, então dois navegadores atrás do mesmo IP não dividem um checkout. Só uma requisição sem nonce (script antigo ou chamada montada à mão) cai no escopo IP (em hash) + User-Agent + janela, em que navegadores distintos atrás do mesmo IP com o mesmo User-Agent e linhas idênticas recebem o mesmo checkout. O nonce fica em `sessionStorage`: uma aba nova gera outro nonce, e nela o clique duplo de um clique antigo de outra aba vira um carrinho novo (inofensivo: só um carrinho vira pedido).

**Uma única instância.** Limitadores de taxa, a espera por requisição concorrente da idempotência, a fila de eventos de catálogo, o cache de tokens e o estado do circuit breaker são em memória. Com duas instâncias, cada uma aplicaria limites próprios, duas requisições do mesmo carrinho poderiam criar dois carrinhos e um webhook poderia ser relido duas vezes. Escalar horizontalmente exigiria mover esse estado para fora do processo.

## 9. Termos da Shopify

A pesquisa não encontrou, em shopify.dev, help.shopify.com, shopify.com/legal nem no changelog, nenhum texto oficial que **permita** ou **proíba** levar um carrinho montado em uma loja ao checkout de outra loja do mesmo lojista [PT-126]. A documentação descreve o mecanismo que o serviço usa (redirecionar para `cart.checkoutUrl` ou para um permalink de carrinho [PT-110]), e descreve lojas como independentes; não trata do caso em que a origem é outra loja Shopify.

Cláusulas que a pesquisa cita como relevantes, para o lojista ler e levar à Shopify (os números de item foram lidos por ferramenta automática e devem ser confirmados na página):
